The event reader consumes the BLOCK header plus its declared transaction-line count and advances past that payload. Processing sets current event time and expires existing entries before dispatch; a banned peer is ignored. For this reorganization path the block must be new, pass proof of work, Merkle, first-coinbase-only structure and noncoinbase-size checks, have a known nonrejected parent, and pass parent-relative height, required difficulty, median-time and future-drift checks. Unknown parents enter the orphan path instead. Noncoinbase transactions are checked/applied in block order against a copied parent snapshot, with spent tracking, existing inputs, maturity, signatures, known positive outputs and no overspend; coinbase is checked against reward plus fees and applied. The valid record is stored and accepted/logged before the strict greater-cumulative-work comparison (parent work plus 16^difficulty). Equal work keeps the current tip. The fork helper aligns heights then walks parents to the common ancestor. Disconnection depth is old-tip height minus fork height; connection count is target height minus fork height. If depth>MAXREORG, REFUSE logs candidate work/fork/depth and returns before tip change or mempool rebuild. The valid candidate remains stored and accepted, visible as STALE with a larger stored count; current TIP/active UTXO, confirmed transactions and pool survive this refusal apart from the expiry already done at event start. No REORG history entry or RETURN is added for that refused switch. Otherwise active tip/chain/confirmed membership changes to the target snapshot; this represents disconnecting old branch spends/outputs and connecting the already validated target branch, rather than executing a literal reverse-apply loop. Old-branch coinbases are excluded from returned transactions. Returned noncoinbase transactions are collected in increasing old-main-chain height and within-block order, then retried before the previous mempool in its insertion order. All returned attempts get current event time as arrival; surviving old entries retain their saved arrival. Newly confirmed transactions are silently skipped. Each other candidate is checked anew against target-tip UTXO at next height and the partially rebuilt pool; failure records DROP, and an accepted returned candidate logs RETURN before register. Pending outputs are not applied to active UTXO, so a pending parent alone cannot satisfy a missing on-chain input. Conflicting pending spends are replaced only when the new fee is strictly greater than their combined fees and its rate strictly exceeds every conflicting entry; replaced entries log DROP replaced. After each insertion, capacity overflow evicts the lowest fee-rate entry, using greatest txid on equal rate, with DROP mempool-full; even a just-returned transaction can be evicted immediately. Later old candidates can replace or evict earlier returned ones. Thus RETURN denotes reacceptance at that point, not a guarantee of final retention. A successful switch logs REORG with fork/disconnected/connected counts and saves old/new hashes, then rebuilds the pool. The received-block handler also resolves queued descendants through the same validation/greater-work path; reports read the resulting actual final tip. At the next event time t2, expiry runs first again with t2-arrival>=EXPIRY: returned entries are aged from this event, old surviving entries from their original arrival; rebuilding does not refresh old ages and no second expiry pass occurs inside the rebuild. log.txt receives accepted/REORG or REFUSE, RETURN and DROP events at current time. chain.txt draws TIP and active BLOCK rows from the chosen chain, STALE from stored nonmain records, REORG history and ranked MEMPOOL rows including arrival times. balances.csv uses active UTXO for balance/count/immature and surviving pool inputs/outputs for locked/incoming; utxo.txt enumerates active coins with new height/category/maturity/lock state, total and root. history.txt walks only the active chain and then surviving pending entries, so disconnected confirmations disappear or become pending only if reaccepted. Ledger balances do not include unconfirmed returned outputs.

Tuple references compare by value; ranked sorts a cloned Vec.
