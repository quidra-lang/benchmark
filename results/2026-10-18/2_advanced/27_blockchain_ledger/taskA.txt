[Overview]
Write a program that simulates a single node of a blockchain, a simplified model of how a cryptocurrency works.
The node processes the events written in an input file in order. The events are: payments from the wallets managed by the node (PAY), raising the fee of an unconfirmed payment (BUMP), transactions (TX) and blocks (BLOCK) received from other nodes (called "peers" below), mining of a block by this node itself (MINE), queries of the state of a transaction (STATUS), and printing of the state (PRINT).
Transactions follow the UTXO (unspent transaction output) model. A transaction consists of inputs (references to outputs of earlier transactions), outputs (a destination address and an amount) and signatures, and the difference between the total of the inputs and the total of the outputs is the fee. The hash function, addresses and signatures are simple ones defined in this statement and have no cryptographic security. Unconfirmed transactions are kept in a mempool and are put into mined blocks in decreasing order of fee rate. The mempool performs replacement by a transaction that raises the fee sufficiently, eviction by a limit on the number of transactions, and removal by expiry.
A block has a header consisting of a height, the hash of the previous block, a Merkle root, a timestamp, a difficulty and a nonce. Mining searches for a nonce until the hash of the header starts with as many "0" characters as the difficulty (proof of work). The difficulty is adjusted from the timestamps every fixed number of blocks, and the block reward is halved every fixed number of blocks.
A block received from a peer is checked for proof of work, Merkle root, structure, size, height, difficulty, timestamp, each transaction it contains (double spending, nonexistent outputs, immature coinbase, signatures, amounts) and the coinbase amount, and is accepted or rejected. A block whose parent is unknown is kept temporarily as an orphan and is processed again when its parent arrives. When there are forks, the chain with the largest cumulative work is the main chain (on a tie, the one that was the main chain first is kept), and when the main chain switches (a reorganization), the transactions of the blocks that left the main chain are returned to the mempool. However, a reorganization that is too deep is refused. A peer that sends invalid data is penalized, and once its score reaches a certain value, data from that peer is ignored from then on.
As the result, the program writes an event log, a summary of the main chain, the wallet balances, the UTXO set and the transaction history of each wallet to 5 files in the output/ folder. It prints nothing to standard output.
All computation is done with integers; no floating-point numbers are used. No random numbers are used either, so the result is uniquely determined. Use only the standard library.

[Input files]
There are 3 input files: input/params.txt, input/wallets.txt and input/events.txt. Every file consists only of ASCII characters, and every line (including the last one) ends with a line feed (LF). There are no empty lines and no spaces at the start or end of a line. The items within a line are separated by single spaces. Every integer is 0 or more and is written in decimal without extra leading zeros (0 is written as "0"). Hexadecimal strings consist only of digits and the lowercase letters a to f. In the descriptions below, <...> marks a part where a value goes; the angle brackets themselves appear in neither the input nor the output.

== input/params.txt (settings) ==
The following 13 lines appear in this order. The first word of each line is in uppercase letters exactly as shown.
- "DIFFICULTY <D0>": the initial difficulty D0 (section 5.4).
- "RETARGET <R> <T>": the interval R (in blocks) at which the difficulty is adjusted, and the target time interval T between blocks (section 5.4).
- "REWARD <R0> <Hh>": the initial block reward R0 and the interval Hh (in blocks) at which the reward is halved (section 5.3).
- "MATURITY <M>": the number of blocks M until a coinbase output becomes spendable (section 4.5).
- "MAXBLOCK <S>": the upper limit S of the size of a block (in characters) (sections 5.1, 9.6, 9.7).
- "MINFEERATE <F>": the minimum fee rate F of a transaction to be put into the mempool (the fee per 1000 characters of transaction size) (section 7.2).
- "MEMPOOL <N>": the upper limit N on the number of transactions the mempool can hold (section 7.3).
- "ORPHANS <K>": the upper limit K on the number of blocks the orphan pool can hold (section 9.7).
- "DRIFT <W>": the allowance W by which the timestamp of a block may be ahead of the current time (section 9.7).
- "EXPIRY <E>": the validity period E of a transaction in the mempool (section 9.1).
- "MAXREORG <Q>": the upper limit Q on the depth of an allowed reorganization (section 8).
- "BAN <Z> <Pb> <Pt>": the score Z at which a peer is banned, the penalty Pb per invalid block, and the penalty Pt per invalid transaction (section 10).
- "GENESIS <name1> <amount1> <name2> <amount2> ...": the amounts distributed in the genesis block (section 5.6). One or more name-amount pairs follow. Each name is the name of a wallet in wallets.txt, and the names are distinct.

== input/wallets.txt (wallets) ==
Each line describes one wallet and has the form "<name> <secret key>". The name is a string of 1 to 10 lowercase letters, and the names are distinct. The secret key is a string of 8 to 16 characters consisting of letters and digits. The order of these lines is called "wallet order".

== input/events.txt (events) ==
The events in the order in which they are processed. Each event starts with one line of the form "<time> <kind> ...". Only for a BLOCK event, transaction lines follow that line. The time is an integer of 0 or more and is at least the time of the previous event. Below, the time of the event being processed is called the "current time" and is denoted by t. There are the following 7 event forms.
- "<t> PAY <sender> <fee> <destination1> <amount1> <destination2> <amount2> ...": send <amount> from the wallet <sender> to each <destination> wallet and pay the fee <fee> (section 9.3). One or more destination-amount pairs follow. <sender> and <destination> are wallet names.
- "<t> BUMP <txid> <fee>": create a transaction that raises the fee of the transaction <txid> in the mempool to <fee> (section 9.4). <txid> is a 32-character hexadecimal string.
- "<t> TX <peer> <transaction text>": a transaction has arrived from a peer (section 9.5).
- "<t> MINE <wallet>": this node mines a block and pays the reward to <wallet> (section 9.6).
- "<t> BLOCK <peer> <height> <previous hash> <merkle root> <timestamp> <difficulty> <nonce> <n>": a block has arrived from a peer (section 9.7). <previous hash> and <merkle root> are 32-character hexadecimal strings. This line is followed by n lines (n >= 1), each holding one transaction text of the block, in their order within the block. These n lines are also part of this event.
- "<t> STATUS <txid>": query the state of the transaction <txid> (section 9.8). <txid> is a 32-character hexadecimal string.
- "<t> PRINT": write the state of the node to the log (section 9.9).
<peer> is a string of 1 to 10 characters consisting of lowercase letters and digits. The form of a transaction text is defined in section 4.1.

[Processing]
== 1. Notation and common rules ==
- All computation is done with integers. For an integer a >= 0 and a positive integer b, a div b is the integer obtained by truncating the fractional part of a / b, and a mod b is its remainder. No negative number is ever divided in this task.
- Strings are compared in lexicographic order, comparing ASCII codes one character at a time from the start.
- The "short form" of a 32-character hexadecimal string (a block hash or a transaction txid) is its first 8 characters. Below, wherever <...8> is written, write the short form of that hash or txid.
- Every line written to the log (output/log.txt) starts with "<t> " (the current time and one space). Below, 'write "X" to the log' means appending the line "<t> X" to the end of the log.

== 2. Hash function and Merkle root ==
2.1 Hash function H: from a string s of length n consisting only of ASCII characters, compute the 32-character hexadecimal string H(s) as follows. Let P = 2147483647, and define the base B_k and the initial value I_k of each of the 4 lanes k = 1, 2, 3, 4 as follows.
  B_1 = 1000003, I_1 = 11
  B_2 = 1500007, I_2 = 23
  B_3 = 2750159, I_3 = 37
  B_4 = 4194301, I_4 = 53
In each lane, start with h = I_k and absorb the characters of s one at a time from the start, absorbing the ASCII code c of each character by h <- (h * B_k + c) mod P. After all characters have been absorbed, absorb the 3 values n, 0, 0 in this order with the same formula (using each value in place of c). Write the resulting h (0 <= h < P) in lowercase hexadecimal, padded on the left with zeros to 8 characters. H(s) is the 32 characters obtained by concatenating the 8 characters of lanes 1, 2, 3, 4 in this order. Since h * B_k + c is less than 2^53, it can be computed exactly with either 64-bit integers or double-precision floating-point numbers.
Example: for s = abc (n = 3), h of lane 1 changes as 11, 11000130, 751760554, 1798911059, 1616895985, 268319539, 852200555, and the hexadecimal form of the last value is 32cb8c6b. Similarly, lanes 2, 3, 4 give 175fc192, 6f462426, 4e978671, so H(abc) = 32cb8c6b175fc1926f4624264e978671.
2.2 Merkle root: from a sequence x_1, ..., x_m of one or more 32-character hexadecimal strings, compute one string as follows. Repeat the following operation until the length of the sequence becomes 1; the one remaining element is the Merkle root. Operation: if the length of the sequence is odd, append one copy of the last element (the same string) to the end of the sequence. Then split the sequence into pairs of two elements from the start, and replace each pair (a, b) with H(the 64-character string formed by concatenating a and b in this order); the resulting sequence (half as long) is the new sequence. If m = 1, x_1 itself is the Merkle root.

== 3. Wallets ==
3.1 Address: the address of a wallet whose secret key is <secret key> is the first 16 characters of H("addr:<secret key>"). For example, if the secret key is Secret1A, the address is 3bf063f6107af1b5. In the input data, the wallet addresses are distinct. An address equal to the address of some wallet is called a "known address", and that wallet is called the "owner of the address".
3.2 Signature: the signature Sign(<secret key>, i, <body>) made with the secret key <secret key> for the input number i (counted from 0) and the string <body> is the first 16 characters of H("<secret key>:<i>:<body>"). <i> is i written in decimal.

== 4. Transactions ==
4.1 Transaction text: a transaction is represented by a one-line string (containing no spaces) of one of the following 2 forms.
- Regular transaction: "in=<input_1>,<input_2>,...,<input_m>;out=<output_1>,<output_2>,...,<output_k>;sig=<signature_1>,<signature_2>,...,<signature_m>"
- Coinbase transaction: "cb=<height>;out=<output_1>,<output_2>,...,<output_k>"
An <input> has the form "<txid>:<index>" and refers to output number <index> (counted from 0) of the transaction whose txid is <txid>. This reference (the pair of a txid and an index) is called an "output reference". An <output> has the form "<address>:<amount>". <txid> is a 32-character hexadecimal string, <address> and <signature> are 16-character hexadecimal strings, and <index>, <amount> and <height> are integers of 0 or more. Every transaction text in the input files has this form, with m >= 1 and k >= 1, and the number of signatures of a regular transaction equals the number of inputs m. However, it is not guaranteed that the referenced outputs exist, that the addresses are known, that the amounts and signatures are correct, and so on (checking these is part of the processing).
4.2 txid, size, body: the txid of a transaction is H(transaction text). The "size" of a transaction is the number of characters of its transaction text. The "body" of a regular transaction is the part of the transaction text before ";sig=" (that is, "in=...;out=...").
4.3 Creating a transaction: when this node creates a regular transaction from a list of inputs (a list of output references), a list of outputs (a list of address-amount pairs) and a secret key used for signing, it builds the transaction text as follows. The body is the concatenation, in this order, of "in=", the inputs "<txid>:<index>" joined with ",", ";out=", and the outputs "<address>:<amount>" joined with ","; the i-th signature (counted from 0) is Sign(secret key, i, body). The transaction text is the concatenation, in this order, of the body, ";sig=", and the signatures joined with ",". A coinbase transaction is built as "cb=<height>;out=" followed by the outputs joined with "," in the same way. All numbers are written in decimal without extra leading zeros.
4.4 UTXO set: a UTXO set is a map from output references to "coins" (address, amount, creation height, whether it is a coinbase coin). To "apply" a transaction at height h means to remove the reference of each input of the transaction from the UTXO set, and then, for each output j (counted from 0) of the transaction, to add the coin (address of the output, amount of the output, h, whether the transaction is a coinbase transaction) under the reference (txid of the transaction, j). The "owner" of a coin is the owner of its address.
4.5 Maturity: a coin is said to be "mature at height h" if it is not a coinbase coin, or its creation height is 0, or h >= (creation height) + M.
4.6 Transaction check: a regular transaction is checked against a UTXO set U, a set X of spent references and a height h. Examine the following conditions in the order (a), (b), (c); the reason (the string in quotes) of the first one that applies is the result of the check. If none applies, the transaction passes the check, and its fee is (the total amount of the coins referenced by the inputs) - (the total amount of the outputs).
(a) If some output has an address that is not known or an amount of 0: "bad-output".
(b) Examine the inputs one at a time from the first (i = 0, 1, ...). If the reference of the input is in X, or is the same as the reference of an earlier input of the same transaction: "double-spend". Otherwise, if the reference is not in U: "missing-input". Otherwise, if the referenced coin is not mature at height h: "immature". Otherwise, if the i-th signature differs from Sign(secret key of the owner of the coin, i, body of the transaction): "bad-sig".
(c) If the total amount of the coins referenced by the inputs is less than the total amount of the outputs: "overspend".
By the processing steps, the address of every coin that enters a UTXO set is always a known address.

== 5. Blocks ==
5.1 Header and hash: a block consists of 6 values, namely the height, the previous hash (the hash of the parent block), the Merkle root, the timestamp, the difficulty and the nonce, and a list of one or more transactions. In a valid block, the first transaction of the list is a coinbase transaction. The "header text" is "<height>|<previous hash>|<merkle root>|<timestamp>|<difficulty>|<nonce>", and the hash of the block is H(header text). The "size" of a block is the total size of the 2nd and later transactions of its transaction list.
5.2 Proof of work and work: a block satisfies proof of work if its hash starts with <difficulty> or more consecutive "0" characters (if the difficulty is 0, it is always satisfied). The work of a block with difficulty b is 16^b. The "cumulative work" of a stored block is the cumulative work of its parent plus the work of the block; the cumulative work of the genesis block is 1.
5.3 Reward: the reward Reward(h) of a block at height h is the value obtained by dividing R0 by 2 and rounding down, repeated (h div Hh) times.
5.4 Required difficulty: the required difficulty Req(p) of a block at height h (= height of p + 1) whose parent is the stored block p is determined as follows.
- If h = 1: D0.
- Otherwise, if h mod R != 0: the difficulty of p.
- Otherwise (h mod R = 0): let q be the block at height h - R reached by following parents from p, and let span = (timestamp of p) - (timestamp of q) and expected = T * (R - 1). If 2 * span < expected: min(difficulty of p + 1, 2); otherwise, if span > 2 * expected: max(difficulty of p - 1, 0); if neither: the difficulty of p. span can be negative.
5.5 Median time: the median time MTP(p) of a stored block p is obtained by sorting in increasing order the timestamps of the 3 blocks p, the parent of p and the parent of the parent of p (only 1 or 2 blocks, up to the genesis block, if the genesis block is reached on the way) and taking the value at position (count - 1) div 2, counting from 0.
5.6 Genesis block: the transactions of the genesis block are a single coinbase transaction of height 0, whose outputs are the pairs (address of <name>, <amount>) of the GENESIS line in the order written. The genesis block has height 0, a previous hash consisting of 32 "0" characters, the txid of this transaction as its Merkle root, and timestamp, difficulty and nonce all 0. The genesis block is not checked.

== 6. Node state ==
The node has the following state.
- Block tree: the collection of stored blocks, which can be looked up by hash. For each stored block, it records the block itself, its cumulative work, the UTXO set with everything up to and including that block applied, its fees (the total fee of the regular transactions of that block) and its source. The source is the name of the peer for a block received from a peer, local for a block mined by this node, and genesis for the genesis block. Initially only the genesis block is stored. Its UTXO set is the empty UTXO set with the transaction of the genesis block applied at height 0.
- Tip: one of the stored blocks. Initially it is the genesis block. The sequence of blocks linked by parent-child relations from the genesis block to the tip is called the "main chain". The transactions contained in the blocks of the main chain (including coinbase transactions) are called "main-chain transactions", and each has the height of the block that contains it. The height of the tip + 1 is called the "next height". Below, "the UTXO set" without qualification means the UTXO set of the tip.
- Mempool: a list of entries (transaction, fee, arrival time) of unconfirmed transactions. The order of this list is called "mempool order". A reference that is the reference of some input of some transaction in the mempool is called a "locked reference".
- Orphan pool: a list of pairs of a block whose parent is unknown and the peer that sent it (in order of arrival).
- Rejected set: the set of hashes of rejected blocks.
- Drop record: for each txid, the reason of the last DROP line (sections 7.3, 7.4) written for that txid.
- Peer records: for each peer, the number of accepted blocks, the number of rejected blocks, the number of blocks put into the orphan pool, the number of accepted transactions, the number of rejected transactions, the number of ignored events, and the score. The record of a peer is created with all values 0 when the name of the peer first appears in a TX or BLOCK event.
- Rejection tally: the number of rejections for each pair of a category (one of block, bump, pay, tx) and a reason.
- Reorganization history: one entry is added each time a reorganization is performed in section 8.

== 7. Mempool ==
7.1 Priority order: for mempool entries a and b, a comes first if (fee of a) * (size of the transaction of b) > (fee of b) * (size of the transaction of a). When both sides are equal, the one with the smaller txid comes first. This order is called "priority order", and the last entry in priority order is called the "lowest-priority entry".
7.2 Acceptance check: decides whether a transaction can be accepted into the mempool in its current state. Examine the following (a) to (e) in order; the reason of the first one that applies is the result of the check.
(a) If it is a coinbase transaction: "coinbase".
(b) If its txid equals the txid of a main-chain transaction or the txid of a transaction in the mempool: "duplicate".
(c) Perform the transaction check (section 4.6) with the UTXO set, an empty set X and the next height; if it fails, the result of that check.
(d) With f the fee and s the size of the transaction, if f * 1000 < F * s: "low-fee".
(e) The mempool entries that have among their inputs a reference equal to some input of the transaction, collected in mempool order, are called the "conflicts". If there is at least one conflict and the following 2 conditions are not both satisfied: "conflict". Condition 1: f is greater than the total fee of the conflicts. Condition 2: for every conflict c, f * (size of the transaction of c) > (fee of c) * s.
If none applies, the transaction is "acceptable", and the result of the check is the fee f and the conflicts.
7.3 Registration and DROP: to "DROP" an entry means to remove it from the mempool if it is there, update the reason for its txid in the drop record, and write "DROP <txid8> <reason>" to the log. To "register" a transaction judged acceptable with a given arrival time, do the following in order.
- DROP each conflict entry, in mempool order, with reason replaced.
- Append the entry (transaction, fee, arrival time) to the end of the mempool.
- If the number of mempool entries exceeds N, DROP the lowest-priority entry (it may be the entry just added) with reason mempool-full.
7.4 Rebuild: when the tip changes in section 8, the mempool is rebuilt using the list of returned transactions. Save the current list of mempool entries as L and empty the mempool. Then, as candidates, process each transaction of the list of returned transactions (with arrival time t) in its order, followed by each entry of L (with the arrival time of that entry) in its order, one at a time, as follows.
- A candidate whose txid equals the txid of a main-chain transaction is discarded without writing anything.
- Otherwise, perform the acceptance check. If it is not acceptable, update the reason in the drop record to the result of the check and write "DROP <txid8> <reason>" to the log. If it is acceptable, write "RETURN <txid8>" to the log only when the candidate is a returned transaction, and register it with the given arrival time.

== 8. Switching the tip ==
To switch the tip to a newly stored block X, process as follows.
Let F (the fork point) be the highest of the blocks contained both in the main chain and in the sequence of blocks linked by parent-child relations from the genesis block to X. Let d = (height of the tip) - (height of F) and c = (height of X) - (height of F).
- If d > Q, leave the tip unchanged, write "REFUSE <height of X> <hash8 of X> work <cumulative work of X> fork <height of F> depth <d>" to the log, and finish.
- Otherwise, set the tip to X. If d = 0, write "TIP <height of X> <hash8 of X> work <cumulative work of X>" to the log. If d >= 1, write "REORG <height of X> <hash8 of X> work <cumulative work of X> fork <height of F> disconnected <d> connected <c>" to the log and add (t, height of F, d, c, hash of the tip before the switch, hash of X) to the reorganization history. Finally, rebuild the mempool (section 7.4). The list of returned transactions consists of the regular transactions (excluding coinbase transactions) of the d blocks of the main chain before the switch that are higher than F, in increasing order of block height and, within the same block, in their order within the block (it is empty if d = 0).

== 9. Event processing ==
Process the events one at a time in order. For each event, first perform section 9.1, then, for TX and BLOCK events, perform section 9.2, and then perform the processing for the kind of the event.

9.1 Expiry: examine the mempool entries in mempool order, and DROP each entry that satisfies t - (arrival time) >= E with reason expired.

9.2 Banned peers: create the record of <peer> if it does not exist. If the score of <peer> is Z or more, add 1 to the number of ignored events of that peer, write "IGNORE <peer> <kind>" (<kind> is TX or BLOCK) to the log, and finish processing this event (for BLOCK, including the n lines that follow).

9.3 PAY: let total be the total of the destination amounts, and need = total + <fee>. Sort the coins that satisfy all of the following conditions in decreasing order of amount (ties: increasing txid of the reference, then increasing index): it is in the UTXO set, its address is the address of <sender>, its reference is not locked, and it is mature at the next height. Select coins one at a time in this order, and stop as soon as the total sum of the selected amounts is need or more.
- If sum < need even after all coins have been selected, write "PAY <sender> fee <fee> total <total> rejected insufficient-funds" to the log and add 1 to (pay, insufficient-funds) in the rejection tally.
- Otherwise, create a transaction (section 4.3) with the secret key of <sender>, using as the list of inputs the references of the coins in the order selected, and as the list of outputs the (address, amount) of each destination in the order written, followed at the end, if sum > need, by (address of <sender>, sum - need). If the acceptance check of this transaction does not find it acceptable, write "PAY <sender> fee <fee> total <total> tx <txid8> rejected <reason>" to the log and add 1 to (pay, reason) in the rejection tally. If it is acceptable, write "PAY <sender> fee <fee> total <total> tx <txid8> accepted inputs <number of inputs> outputs <number of outputs> size <size>" to the log and register it with arrival time t.

9.4 BUMP: write <id8> for the short form of <txid>.
- If the mempool has no entry whose txid is <txid>, write "BUMP <id8> fee <fee> rejected unknown" to the log and add 1 to (bump, unknown) in the rejection tally.
- Otherwise, let e be the transaction of that entry and fe its fee. Let A be the set of addresses of the coins referenced by the inputs of e (they are in the UTXO set), let (a, v) be the last output of e, and let v' = v - (<fee> - fe). If A is not the set consisting of the address a alone, or v' < 1, write "BUMP <id8> fee <fee> rejected no-change" to the log and add 1 to (bump, no-change) in the rejection tally.
- Otherwise, create a new transaction with the secret key of the owner of a, from the same list of inputs as e (in the same order) and the list of outputs of e with only the last amount changed to v'. If the acceptance check of the new transaction does not find it acceptable, write "BUMP <id8> fee <fee> tx <txid8 of the new transaction> rejected <reason>" to the log and add 1 to (bump, reason) in the rejection tally. If it is acceptable, write "BUMP <id8> fee <fee> tx <txid8 of the new transaction> accepted size <size of the new transaction>" to the log and register it with arrival time t (e is DROPped as a conflict with reason replaced).

9.5 TX: perform the acceptance check on the transaction given by the transaction text.
- If it is not acceptable, add 1 to the number of rejected transactions of <peer> and 1 to (tx, reason) in the rejection tally, and write "TX <peer> <txid8> rejected <reason>" to the log. If the reason is one of coinbase, bad-output, bad-sig and overspend, penalize <peer> by Pt points (section 10).
- If it is acceptable, add 1 to the number of accepted transactions of <peer>, write "TX <peer> <txid8> accepted fee <fee> size <size>" to the log, and register it with arrival time t.

9.6 MINE: create and store a block as follows.
(1) Let h be the next height. Examine the mempool entries one at a time in priority order, and select an entry if the total size of the transactions selected so far plus the size of its transaction is S or less (an entry that would make the total exceed S is skipped, and the next entry is examined). Let fees be the total fee of the selected entries.
(2) Create the coinbase transaction "cb=<h>;out=<address of the wallet>:<Reward(h) + fees>". The transaction list is this coinbase transaction followed by the selected transactions in priority order.
(3) The height is h, the previous hash is the hash of the tip, the Merkle root is the Merkle root of the sequence of txids of the transaction list, the timestamp is max(t, MTP(tip) + 1), the difficulty is Req(tip), and the nonce is the smallest integer of 0 or more that satisfies proof of work (try 0, 1, 2, ... in this order).
(4) Store this block without checking it. Its UTXO set is the UTXO set of the tip with each transaction of the transaction list applied in order at height h, its fees are fees, and its source is local. Write "MINE <wallet> <h> <hash8> bits <difficulty> nonce <nonce> txs <number of transactions (including the coinbase transaction)> size <size of the block> fees <fees> work <cumulative work>" to the log, and switch the tip to this block (section 8). Orphan resolution (section 9.7) is not performed for a mined block.

9.7 BLOCK: compute the hash of the received block and do the first of the following (1) to (4) that applies. Below, <h> is the height written in the header.
(1) If the hash equals the hash of a stored block, the hash of a block in the orphan pool, or a hash in the rejected set, write "BLOCK <peer> <h> <hash8> rejected duplicate" to the log, add 1 to the number of rejected blocks of <peer> and 1 to (block, duplicate) in the rejection tally, and finish (no penalty is given).
(2) Examine the following conditions in order; if one applies, reject the block with that reason (rejection procedure, with kind BLOCK), perform orphan resolution starting from the hash of this block, and finish.
- If it does not satisfy proof of work: "bad-pow".
- If the Merkle root of the sequence of txids of the transaction list differs from the Merkle root in the header: "bad-merkle".
- If the first transaction is not a coinbase transaction, or its <height> differs from the height in the header, or there is a coinbase transaction among the 2nd and later transactions: "bad-structure".
- If the size of the block exceeds S: "too-large".
- If the previous hash is in the rejected set: "bad-parent".
(3) If the block with the previous hash is not stored, append (block, <peer>) to the end of the orphan pool, add 1 to the number of blocks put into the orphan pool of <peer>, and write "BLOCK <peer> <h> <hash8> orphan parent <previous hash8>" to the log. If the number of blocks in the orphan pool exceeds K, remove the first one (the oldest) and write "EVICT <hash8 of the removed block> orphan-limit" to the log. Then finish.
(4) If none of the above applies, perform block connection (with kind BLOCK), and then perform orphan resolution starting from the hash of this block.

Block connection: for a kind (BLOCK or UNORPHAN), a block and a peer, using the stored parent p, examine the following (a) to (f) in order; if one applies, reject the block with that reason (rejection procedure) and finish.
(a) If the height in the header differs from the height of p + 1: "bad-height".
(b) If the difficulty differs from Req(p): "bad-difficulty".
(c) If the timestamp is MTP(p) or less: "time-too-old".
(d) If the timestamp is greater than t + W: "time-too-new".
(e) Let U be a copy of the UTXO set of p, X an empty set and fees = 0, and examine the 2nd and later transactions in order (with position in the block k = 2, 3, ...). Perform the transaction check with U, X and the height in the header; if it fails: "<result of the check> tx <k>" (example: bad-sig tx 2). If it passes, add all references of the inputs of the transaction to X, apply the transaction to U at the height in the header, and add its fee to fees.
(f) If some output of the first transaction (the coinbase transaction) has an address that is not known or an amount of 0: "bad-output tx 1". Otherwise, if the total amount of its outputs is greater than Reward(height in the header) + fees: "bad-coinbase".
If none applies, apply the coinbase transaction to U at the height in the header and store the block (its cumulative work is the cumulative work of p + its work, its UTXO set is U, its fees are fees, and its source is the name of the peer). Add 1 to the number of accepted blocks of the peer, and write "<kind> <peer> <h> <hash8> accepted work <cumulative work>" to the log. If the cumulative work of this block is greater than the cumulative work of the tip, switch the tip to this block (section 8).

Rejection procedure: for a kind, a block, a peer and a reason, add the hash of the block to the rejected set, add 1 to the number of rejected blocks of the peer, add 1 to (block, first word of the reason) in the rejection tally (for example, if the reason is bad-sig tx 2, this is (block, bad-sig)), and write "<kind> <peer> <h> <hash8> rejected <reason>" to the log. Unless the reason is time-too-new, penalize the peer by Pb points (section 10).

Orphan resolution: prepare a queue that contains only the starting hash, and repeat the following until the queue is empty. Take the hash u from the front of the queue. Process the blocks in the orphan pool whose previous hash is u, one at a time in orphan pool order, as follows: remove the block from the orphan pool; if u is in the rejected set, reject the block with kind UNORPHAN and reason bad-parent (rejection procedure), otherwise perform block connection with kind UNORPHAN; regardless of the result, append the hash of that block to the end of the queue. The peer records are updated and penalties are given for the peer that sent that block.

9.8 STATUS: let <id8> be the short form of <txid>, and write the first of the following lines that applies to the log.
- If there is a main-chain transaction whose txid is <txid>, with g its height: "STATUS <id8> confirmed <g> confirmations <next height - g>".
- If it is in the mempool, with r its position in priority order (counted from 1) and m the number of mempool entries: "STATUS <id8> mempool rank <r> of <m>".
- If it is in the drop record: "STATUS <id8> dropped <reason>".
- If it is contained in some stored block: "STATUS <id8> stale".
- If none of these applies: "STATUS <id8> unknown".

9.9 PRINT: write the following lines to the log in this order.
- "PRINT height <height of the tip> tip <hash8 of the tip> work <cumulative work of the tip> bits <Req(tip)> reward <Reward(next height)> mempool <number of mempool entries> size <total size of the mempool transactions> orphans <number of blocks in the orphan pool>"
- For each mempool entry, in priority order: "MEMPOOL <rank> <txid8> fee <fee> size <size>" (the rank is counted from 1).
- For each wallet, in wallet order: "BALANCE <name> <total amount of the coins in the UTXO set whose address is the address of that wallet>".

== 10. Penalties and bans ==
To penalize a peer by p points, add p to the score of that peer. If the score before adding is less than Z and the score after adding is Z or more, write "BAN <peer> score <score after adding>" to the log. A peer whose score is Z or more is called a "banned peer". Banned peers continue to be penalized, but no BAN line is written for them.

[Output files]
The program writes 5 files: output/log.txt, output/chain.txt, output/balances.csv, output/utxo.txt and output/history.txt. Every file consists only of ASCII characters, and every line (including the last one) ends with a line feed (LF). There are no trailing spaces and no empty lines. Items are separated by single spaces (in balances.csv, by commas ","). Integers are written in decimal without extra leading zeros. Hashes, txids and addresses are written as lowercase hexadecimal strings. Below, the "final state" is the state after all events have been processed.

== output/chain.txt (main chain summary) ==
For the final state, write the following lines in this order.
(1) One line "TIP <height of the tip> <hash of the tip> work <cumulative work of the tip> stored <number of stored blocks (including the genesis block)> orphans <number of blocks in the orphan pool>". The hash is written with all 32 characters.
(2) For each block of the main chain, in increasing order of height, the following line, followed by the line of each transaction of that block in block order.
"BLOCK <height> <hash> prev <previous hash8> time <timestamp> bits <difficulty> nonce <nonce> txs <number of transactions> size <size> fees <fees> miner <miner> source <source> work <cumulative work>"
<miner> is the owner of the address of the first output of the coinbase transaction. For the genesis block only, write "-". With k the position of the transaction within the block (counted from 1), the transaction line is "TX <k> <txid> <category> out <number of outputs> amount <total amount of the outputs>" for a coinbase transaction (<category> is genesis for the transaction of the genesis block and coinbase otherwise), and "TX <k> <txid> payment in <number of inputs> out <number of outputs> size <size> fee <fee>" for a regular transaction. The txid is written with all 32 characters.
(3) For each stored block that is not in the main chain, in increasing order of height (ties: increasing hash): "STALE <height> <hash> prev <previous hash8> source <source> work <cumulative work>".
(4) For each block in the orphan pool, in orphan pool order: "ORPHAN <height in the header> <hash> prev <previous hash8> source <peer>".
(5) For each entry of the reorganization history, in the order added: "REORG <time> fork <height of the fork point> disconnected <d> connected <c> old <hash8 of the tip before the switch> new <hash8 of the tip after the switch>".
(6) For each wallet, in wallet order, if there is at least one block of height 1 or more in the main chain whose miner is that wallet: "MINER <name> blocks <number of those blocks> coinbase <total amount of the outputs of their coinbase transactions> fees <total fees of those blocks>".
(7) Divide the blocks of the main chain from height 1 to the height of the tip into the longest consecutive runs of equal difficulty, and for each run, starting from the run with the smallest heights: "BITS <difficulty> heights <first height of the run>-<last height of the run> blocks <number of blocks in the run>" (nothing is written if the tip is the genesis block).
(8) For each peer, in increasing order of name: "PEER <name> blocks <number of accepted blocks> rejected <number of rejected blocks> orphans <number of blocks put into the orphan pool> txs <number of accepted transactions> rejected <number of rejected transactions> ignored <number of ignored events> score <score> <state>". <state> is banned for a banned peer and ok otherwise.
(9) For each mempool entry, in priority order: "MEMPOOL <rank> <txid> fee <fee> size <size> time <arrival time>" (the rank is counted from 1, and the txid is written with all 32 characters).
(10) For each pair whose count in the rejection tally is 1 or more, in increasing order of category, ties in increasing order of reason: "REJECT <category> <reason> <count>".
(11) One line "SUPPLY genesis <total amount of the outputs of the transaction of the genesis block> rewards <sum of Reward(height) over the blocks of height 1 or more in the main chain> fees <total fees of the blocks of height 1 or more in the main chain> burned <rewards + fees - (total amount of the outputs of the coinbase transactions of the blocks of height 1 or more in the main chain)> utxo <total amount of the coins in the UTXO set>".

== output/balances.csv (balances) ==
The first line is "wallet,address,balance,immature,locked,incoming,utxos". From the 2nd line on, write one line "<name>,<address>,<balance>,<immature>,<locked>,<incoming>,<utxos>" for each wallet in wallet order. Over the coins of the final UTXO set whose address is the address of that wallet, balance is the total amount, immature is the total amount of the coins that are not mature at the next height, locked is the total amount of the coins whose reference is locked, and utxos is the number of coins. incoming is the total amount of the outputs of the mempool transactions whose address is the address of that wallet.

== output/utxo.txt (UTXO set) ==
For each coin of the final UTXO set, in increasing order of the txid of the reference (ties: increasing index), write one line "<txid>:<index> <owner> <amount> height <creation height> <category> <state>". <category> is genesis if the creation height is 0, otherwise coinbase for a coinbase coin, and payment otherwise. <state> is immature if the coin is not mature at the next height, otherwise locked if its reference is locked, and free otherwise.
After that, write the 2 lines "TOTAL <number of coins> <total amount>" and "ROOT <merkle root>". <merkle root> is the Merkle root of the sequence of the values of H of the strings of the coin lines (without the line feed), in line order (it follows from the processing steps that the UTXO set is never empty).

== output/history.txt (transaction history) ==
For each wallet, in wallet order, write the following lines.
(1) One line "WALLET <name> <address>".
(2) Examine the main-chain transactions of the final state in increasing order of block height and, within the same block, in block order; for each transaction that spends a coin of that wallet in its inputs or has the address of that wallet in its outputs, one line "<height> <txid8> <category> spent <S> received <Rv> net <Rv - S> balance <balance>". S is the total amount of those coins referenced by the inputs of the transaction (each is the output with that index of the main-chain transaction that has the txid of the reference) whose owner is that wallet, and Rv is the total amount of the outputs of the transaction whose address is the address of that wallet. <category> is genesis for the transaction of the genesis block, otherwise coinbase for a coinbase transaction, and payment otherwise. <Rv - S> is written with "+" if it is 0 or more and with "-" if it is negative (examples: +30, -123, +0). <balance> is the sum of <Rv - S> over the lines of that wallet up to and including this line.
(3) For each mempool entry, in priority order, compute S (the total amount of those coins in the UTXO set referenced by its inputs whose owner is that wallet) and Rv in the same way, and if at least one of S and Rv is not 0, one line "pending <txid8> spent <S> received <Rv> net <Rv - S>" (the sign is written in the same way as in (2)).
(4) One line "END <name> txs <number of lines of (2)> spent <total of S in (2)> received <total of Rv in (2)> balance <last balance in (2) (0 if there are no lines)> pending <number of lines of (3)>".

[Source files]
Organize the program into the following 6 source files (file names follow the conventions of each language).
- main: holds the overall flow and the core of the processing. Reading params.txt and events.txt; creating the genesis block; managing the node state (block tree, tip, main-chain transactions, mempool, orphan pool, rejected set, drop record, peer records, rejection tally, reorganization history); the processing of each event (expiry, ignoring banned peers, coin selection for PAY, BUMP, TX, block assembly for MINE, the duplicate, orphan, connection and rejection decisions for BLOCK and orphan resolution, STATUS, PRINT); the acceptance check, replacement, registration and rebuild of the mempool; switching the tip (fork point, reorganization, refusal); penalties and bans; and building and writing the lines of all output files (log.txt, chain.txt, balances.csv, utxo.txt, history.txt).
- hashing: the hash function H, the Merkle root and the short form.
- wallets: reading wallets.txt, computing addresses and computing signatures.
- transactions: the representation of transactions, parsing and creating transaction texts, the txid, size and body, the representation of coins, the maturity test, the transaction check, and applying a transaction to a UTXO set.
- blocks: the representation of blocks, the header text and hash, parsing BLOCK events, the nonce search (mining), and the context-free checks (bad-pow, bad-merkle, bad-structure, too-large).
- chain: the representation of the records of stored blocks, the reward, getting ancestors and the sequence of the main chain, the fork point, the median time, and computing the required difficulty.

[Constraints]
- The number of wallets is between 2 and 10 inclusive. The number of GENESIS pairs is between 1 and 10 inclusive, and each amount is between 1 and 1000000 inclusive.
- 2 <= R <= 10, 1 <= T <= 1000, 0 <= D0 <= 2, 1 <= R0 <= 1000000, 1 <= Hh <= 100, and Reward(h) >= 1 for every h with 1 <= h <= 30. 1 <= M <= 10, 100 <= S <= 10000, 0 <= F <= 1000, 1 <= N <= 100, 1 <= K <= 10, 0 <= W <= 1000, 1 <= E <= 1000000, 1 <= Q <= 30, 1 <= Z <= 1000, 0 <= Pb <= 1000, 0 <= Pt <= 1000.
- The number of lines of events.txt (including the transaction lines of BLOCK events) is at most 2000, and the times are at most 1000000.
- The <fee> of PAY is 0 or more, each <amount> is 1 or more, and there are between 1 and 10 destinations. The <fee> of BUMP is 0 or more. The <wallet> of MINE is a wallet name.
- In BLOCK, the height in the header is at most 100, the timestamp is at most 1000000, the difficulty is one of 0, 1, 2, the nonce is at most 1000000, and n is between 1 and 20 inclusive.
- A transaction text has at most 1000 characters, at most 10 inputs and at most 15 outputs.
- Throughout the processing, the height of the main chain is always at most 30 and the number of stored blocks is at most 60. The nonce search of MINE finishes in fewer than 10000 attempts.
- Every integer that appears in the computation, such as amounts, fees, their totals, scores and times, except the intermediate values of computing H, is less than 2^31 (this includes the products in the fee rate comparisons). The intermediate values of computing H are less than 2^53.
