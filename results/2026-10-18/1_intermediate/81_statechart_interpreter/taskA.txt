[Overview]
Write an interpreter for hierarchical state machines (statecharts) that work on the same principles as UML statecharts and SCXML. The program reads one or more charts, one after another, from standard input. Each chart consists of a "definition part", which defines states, variables, actions and transitions, and a "script part", which lists commands that drive the chart. The program first checks the definition part and, if it contains errors, reports them with line numbers. If there are no errors, it warns about unreachable states, starts the chart, executes the commands of the script part in order, and writes logs, traces, dumps of the state and statistics to standard output. The features covered are nested states, parallel states, final states and completion events, shallow and deep history, entry and exit actions, guard expressions with variables, comparisons, logical operators and in(state), internal, external and local transitions, transitions triggered by the passage of time (after) and transitions without an event (always), actions made of assignment, raise, send, cancel and log, delayed events using an internal queue and a logical clock, selection and execution of transitions by the run-to-completion procedure, resolution of conflicts between transitions in parallel regions, and detection of infinite loops (livelock).

[Input format]
The first line contains the number of charts T, followed by T charts in order. One chart consists of the following lines, in this order:

  CHART name
  definition lines (0 or more lines)
  RUN
  script lines (0 or more lines)
  END

name is the name of the chart, a string of 1 to 20 characters consisting only of lowercase English letters, digits and _. The RUN line and the END line each consist of exactly that string.
Every line is a string of 1 to 200 characters consisting only of printable ASCII characters (character codes 32 to 126), with no space at the beginning or end of the line, and there are no empty lines. In the formats below, words are separated by exactly one space (except inside expressions and strings). Inside an expression (section 5 of [Processing]), zero or more spaces may appear between tokens.
The input lines are numbered 1, 2, 3, ... in order, starting from the first line (the line with T). This number is called the "line number".

== How names and values are written ==
- A state name or variable name is a string of 1 to 20 characters that starts with a lowercase English letter and consists only of lowercase English letters, digits and _.
- An event name is a string of 1 to 31 characters that starts with a lowercase English letter and consists only of lowercase English letters, digits, _ and ., in which . never appears two or more times in a row, and whose last character is not ".".
- No state name, variable name or event name is equal to any of the following 10 reserved words: initial, shallow, deep, after, always, in, raise, send, cancel, log
- An integer VALUE is a sequence of digits, optionally preceded by "-". If the sequence of digits has 2 or more characters, it does not start with 0, and the value it represents is at most 1000000. "-0" does not appear.
- A positive integer K is an integer from 1 to 1000 written in decimal without extra leading zeros.
- A string STRING starts with a double quote (") and ends with a double quote, with zero or more printable characters other than the double quote (") and ";" in between.

== Definition lines ==
There are the following 15 formats of definition lines. ID, PARENT, CHILD, DEFAULT, STATE and TARGET are state names, NAME is a variable name, and GUARD is an expression.

  state ID
  state ID PARENT
  state ID initial CHILD
  state ID PARENT initial CHILD
  parallel ID
  parallel ID PARENT
  final ID PARENT
  history ID PARENT shallow
  history ID PARENT deep
  history ID PARENT shallow DEFAULT
  history ID PARENT deep DEFAULT
  var NAME VALUE
  entry STATE / ACTIONS
  exit STATE / ACTIONS
  on STATE TRIGGER

In the last format, the on line, TRIGGER may be followed by each of the following three parts, each one either present or absent, in this order:
- Guard part: " [" (a space and [), GUARD and "]" concatenated in this order.
- Target part: " -> TARGET" or " ~> TARGET".
- Action part: " / ACTIONS".
TRIGGER is one of: always, "after K", or one or more "event descriptors" joined by "|" (with no spaces in between). An event descriptor is an event name or "*".
For example, "on idle coin|token [credit + _data >= 100] -> ready / credit = credit + _data; log "ready"" is an on line that has a guard part, a target part and an action part; "on blink after 3 -> blink" has no action part; and "on main ping / log "pong"" has no target part.

ACTIONS is one or more "actions" separated by "; " (a semicolon followed by one space). There are the following 9 formats of actions. EVENT is an event name, EXPR is an expression, and NAME is a variable name or the string _data.

  NAME = EXPR
  raise EVENT
  raise EVENT EXPR
  send EVENT K
  send EVENT K EXPR
  cancel EVENT
  log STRING
  log EXPR
  log STRING EXPR

== Script lines ==
There are the following 8 formats of script lines. N is an integer from 1 to 10000 written in decimal without extra leading zeros. NAME in set is a variable name or the string _data.

  event EVENT
  event EVENT VALUE
  tick N
  set NAME VALUE
  trace on
  trace off
  eval EXPR
  dump

Every line follows these formats and [Constraints]. Every expression follows the grammar of section 5 of [Processing] and has no space at its beginning or end. However, the states and variables referred to by name do not necessarily exist (how this is handled is explained in [Processing]).

[Processing]
Process the charts one at a time in input order. For each chart, first output "chart <name>". Then check the definition part (section 2); if there are errors, report them and finish processing that chart. If there are no errors, warn about unreachable states (section 3), perform the start macrostep (section 10), execute the commands of the script part in order (section 11), and output the statistics at the END line (section 12). For every chart, all state is created anew; nothing carries over from previous charts.
Below, a string shown in double quotes is a string that appears in the output as is, and a part enclosed in < and > inside it is replaced by its value. Integers are written in decimal, negative numbers with "-", and without extra leading zeros. When a "list" of states is output, the state names are joined with "," (with no spaces), and an empty list is written as "-".

== 1. The state tree ==
The defined states (section 2) form one tree. The root of the tree is the unnamed "root". A state defined without PARENT is called a "top-level state"; top-level states are children of the root. A state defined with PARENT is a child of PARENT. The children of a state are ordered by the line numbers of the lines that define them.
The states that appear while following the parent, the parent's parent, ... of a state up to the root are called the "ancestors" of that state (the root is included; the state itself is not). When A is an ancestor of B, B is called a "descendant" of A (a state is not its own descendant).
The "kind" of a state is the first word (state, parallel, final, history) of the line that defines it. A state of kind history is called a "history state", and a state of kind final is called a "final state". A history state is a special state used as a transition target; it never becomes active (section 4).
- Among the children of a state, those that are not history states are called its "child states".
- A state of kind state that has one or more child states, and the root, are called "compound states".
- A state of kind parallel that has one or more child states is called a "parallel state".
- A state that is not a history state and has no child states is called an "atomic state" (even a state of kind parallel is atomic if it has no child states).
- The "initial child state" of a compound state is CHILD if initial CHILD is written on the line that defines the state, and otherwise its first child state. The initial child state of the root is the first top-level state.
- The "default target" of a history state H is DEFAULT if DEFAULT is written on the line that defines H, and otherwise the initial child state of H's parent.
- The "document order" of states is the order in which states are listed when the following procedure visit is applied to each top-level state in order. visit(s): list s, then apply visit to each child of s (including history states) in order. For example, if "state a", "state b", "state a1 a" are defined in this order, the document order is a, a1, b. The reverse of document order is called "reverse document order". In document order, every state comes before its descendants.
- The "depth" of a state is 1 for a top-level state, and the depth of a child is the depth of its parent plus 1.
- The "name order" for comparing names is the order that compares character codes one character at a time from the beginning, puts first the name whose code is smaller at the first differing character, and, when one name equals the beginning of the other, puts the shorter one first.

== 2. Checking the definition ==
The definition lines are checked in the following two phases. For each line, only the first error found is recorded.

Phase 1: Examine the state, parallel, final, history and var lines in line-number order.
- A state, parallel, final or history line is checked in the following order:
  1. If the state ID has already been defined by an earlier line: "duplicate state <ID>"
  2. If PARENT is written and the state PARENT has not been defined by an earlier line: "unknown state <PARENT>"
  3. If PARENT is written and the kind of the state PARENT is final or history: "<PARENT> cannot have children"
  If none of these applies, the line "defines" the state ID. A line for which an error was recorded defines nothing. For example, if a later line defines the same ID as a line with an error, that is not a duplicate state error.
- For a var line, if the variable NAME has already been declared by an earlier var line, the error is "duplicate variable <NAME>". Otherwise the line "declares" the variable NAME with the initial value VALUE.

Phase 2: Examine all definition lines for which no error was recorded in phase 1, in line-number order. Here a state "is defined" if some line defined it in phase 1, and a variable "is declared" if some var line declared it in phase 1; this includes definitions and declarations by lines after the line being checked.
- A state line containing initial CHILD: if the state CHILD is not defined, "unknown state <CHILD>"; if the parent of CHILD is not ID, or CHILD is a history state, "<CHILD> is not a child of <ID>".
- A final line or a history line: if the kind of PARENT is not state, or PARENT has no child states, "<ID> needs a compound parent".
- A history line containing DEFAULT: if the error above does not apply, continue: if the state DEFAULT is not defined, "unknown state <DEFAULT>"; if DEFAULT is not a descendant of PARENT, or DEFAULT is a history state, "<DEFAULT> is not a descendant of <PARENT>".
- An entry line or an exit line: if the state STATE is not defined, "unknown state <STATE>"; if STATE is a history state, "<STATE> cannot have actions". If neither applies, continue by checking the references in ACTIONS.
- An on line: if the state STATE is not defined, "unknown state <STATE>"; if the kind of STATE is final or history, "<STATE> cannot have transitions". If neither applies, continue by checking the references in GUARD, TARGET and ACTIONS.
When checking references, examine the following "references" in the line in the order in which they appear in the line (left to right), and the first one that does not satisfy its condition is the error.
- A variable name in an expression (except _data), and NAME of an action NAME = EXPR: if the variable is not declared, "unknown variable <that name>".
- S of in(S) in an expression, and TARGET of the target part: if the state is not defined, "unknown state <that name>".
Since _data is not a variable, the action "_data = 1" is the error "unknown variable _data". Event names, and other lines such as var and state lines, have no references checked in phase 2.

If there are one or more errors, output "error line <n>: <error message>" for each line for which an error was recorded, in increasing order of line number, where n is the line number of that line. In this case the script part is not executed, and nothing else is output for that chart.
A chart with no errors is called a "valid chart". Sections 3 to 12 below describe valid charts. In a valid chart, every state name appearing in the definition lines refers to a defined state, every variable name appearing in expressions and assignments (except _data) refers to a declared variable, and the parent of every final state and history state is a compound state.

== 3. Warning about unreachable states ==
Whether a state is "reachable" is determined by the following rules.
1. The initial child state of the root is reachable.
2. Repeatedly make reachable every state that satisfies one of the following, until no new state becomes reachable:
  - The parent of a reachable state (except the root).
  - The initial child state of a reachable compound state.
  - A child state of a reachable parallel state.
  - For the target X of a transition (section 7) whose source is a reachable state: X if X is not a history state, or the default target of X if X is a history state.
For each state that is not a history state and is not reachable, output "warning: unreachable state <ID>", in document order. This determination depends only on the definition; values of guards and the like are not considered.

== 4. Runtime state ==
When running a valid chart, the program keeps the following information.
- Configuration: the set of "active" states. Initially empty. The root and history states are never in the configuration.
- Variables: the value of each declared variable. Initially the VALUE of its var line.
- Current value: the integer that _data denotes in expressions (sections 5 and 10). Initially 0.
- Internal queue: a sequence of events, taken out in the order in which they were added. An event is a pair of an event name and an integer "value". Initially empty.
- Reservation list: a collection of "reservations". There are two kinds of reservation: a "timer", which refers to one after transition, and a "send", which holds one event; both have a "due time" (the time at which the reservation is processed) and a "creation number". The creation number is the number 1, 2, 3, ... assigned in order each time a reservation is created in that chart. Initially empty.
- History values: for each history state, a list of states or "unrecorded". Initially all unrecorded.
- Time: an integer of at least 0. Initially 0.
- Trace: on or off. Initially off.
- Halted: whether the run has halted. Initially not halted.
- Statistics: the number of macrosteps, the number of microsteps, and for each state the entry count, the transition count and the dwell time. Initially all 0. In addition, for each state, the time at which it was last entered (its entry time) is recorded.

== 5. Expressions ==
An expression consists of the following tokens.
- Integer literal: a sequence of one or more digits only. If it has 2 or more characters, it does not start with 0, and the value it represents is at most 1000000.
- Name: a sequence that starts with an English letter or _ and consists only of English letters, digits and _.
- Operators: || && == != <= >= < > + - * / % ! ( )
Spaces only separate tokens and have no other meaning. The grammar of expressions is as follows. { } denotes zero or more repetitions of its contents, and | denotes one of the alternatives.

  expr           = and_expr { "||" and_expr }
  and_expr       = comparison { "&&" comparison }
  comparison     = additive { ( "==" | "!=" | "<" | "<=" | ">" | ">=" ) additive }
  additive       = multiplicative { ( "+" | "-" ) multiplicative }
  multiplicative = unary { ( "*" | "/" | "%" ) unary }
  unary          = ( "!" | "-" ) unary | primary
  primary        = integer_literal | variable_name | "_data" | "in" "(" state_name ")" | "(" expr ")"

All binary operators are left-associative. For example, 10 - 4 - 3 means (10 - 4) - 3, and 3 > 2 > 1 means (3 > 2) > 1. The value of an expression is computed as follows.
- An integer literal is its value, a variable name is the value of that variable, and _data is the current value. in(S) is 1 if the state S is in the configuration, and 0 otherwise.
- !a is 1 if a is 0, and 0 otherwise. -a is a with its sign inverted.
- a + b, a - b and a * b are the sum, difference and product.
- a / b is the quotient of a divided by b with its fractional part discarded (the integer rounded toward 0). a % b is a - (a / b) * b. For example, 7 / -2 is -3, -7 / 2 is -3, -7 % 3 is -1, and 7 % -3 is 1. If b is 0, it is an "evaluation error".
- A comparison operator is 1 if the relation holds, and 0 otherwise.
- a && b: first evaluate a; if a is 0, the result is 0 without evaluating b. If a is not 0, evaluate b; the result is 1 if b is not 0, and 0 if it is 0.
- a || b: first evaluate a; if a is not 0, the result is 1 without evaluating b. If a is 0, evaluate b; the result is 1 if b is not 0, and 0 if it is 0.
- Binary operators other than && and || evaluate the left operand, then the right operand, and then compute.
When an evaluation error occurs, evaluation of the whole expression stops at that point. An expression whose value is not 0 is called "true", and one whose value is 0 is called "false".

== 6. Action lists ==
Each state has a list of "entry action lists", which are the ACTIONS of its entry lines in line-number order, and a list of "exit action lists", which are the ACTIONS of its exit lines in line-number order (the ACTIONS of one line form one action list).
An action list executes its actions from left to right. Each action does the following.
- NAME = EXPR: evaluate EXPR and assign its value to the variable NAME.
- raise EVENT and raise EVENT EXPR: append to the end of the internal queue an event with name EVENT whose value is the value of EXPR (0 if there is no EXPR).
- send EVENT K and send EVENT K EXPR: create a send reservation holding an event with name EVENT whose value is the value of EXPR (0 if there is no EXPR), with due time "current time + K", and add it to the reservation list.
- cancel EVENT: remove from the reservation list all send reservations whose held event has the name EVENT. Timer reservations are not removed. If there is no such reservation, do nothing.
- log STRING: output, as one line, the text between the opening and closing double quotes of STRING.
- log EXPR: output the value of EXPR as one line.
- log STRING EXPR: output, as one line, the text between the opening and closing double quotes of STRING immediately followed, with no space, by the value of EXPR.
When an evaluation error occurs in an expression in an action, that action does nothing (no assignment, no addition to the queue, no reservation, no output), and the remaining actions of that action list are not executed either. Then an event with name error.execution and value 0 is appended to the end of the internal queue. Other action lists (for example, the action list of the next entry line of the same state) are executed unaffected by this.

== 7. Transitions ==
An on line defines one transition whose "source" is STATE. The transitions whose source is a given state are ordered by line number. The action list of a transition is its ACTIONS if it has an action part, and an empty action list otherwise.
- A transition whose TRIGGER is always is called an "eventless transition", one whose TRIGGER is after K is called a "timer transition", and any other transition is called an "event transition".
- The guard of a transition without a guard part is always true. When an evaluation error occurs while evaluating a guard, an event with name error.execution and value 0 is appended to the end of the internal queue, and that guard is considered false.
- A transition without a target part is called an "internal transition", one whose target is written with "->" is called an "external transition", and one written with "~>" is called a "local transition".
For a transition that is not an internal transition, the following are defined.
- The "effective targets" are a list of states determined as follows. If the target X is not a history state, it is the list consisting of X alone. If X is a history state and its value is recorded, it is the recorded list. If it is unrecorded, it is the list consisting of the default target of X alone.
- The "scope" is a state (possibly the root) determined as follows. If the transition is a local transition, the source is a compound state, and every state of the effective targets is a descendant of the source, the scope is the source itself. Otherwise, examine the ancestors of the source from nearest to farthest (parent, parent's parent, ..., root); the scope is the first one found that is a compound state and of which every state of the effective targets is a descendant.
- The "exit set" is the set of all states in the configuration that are descendants of the scope. The exit set of an internal transition is empty.
For example, an external transition whose source is a1, a child of a compound state a, and whose target is a2, another child of a, has scope a, and a is not exited. An external transition whose source is a itself and whose target is a2 has an ancestor of a as its scope, so a is exited once and then entered again. If the same transition is a local transition, its scope is a, and a is not exited. A parallel state is never a scope.

== 8. Selecting transitions ==
Transitions are selected for a "trigger" of one of the following three kinds. For each, a transition "matches" the trigger as defined below.
- An event (a pair of a name E and a value): the transition is an event transition and at least one of its event descriptors matches E. An event descriptor D matches E if D is "*", or D is equal to E, or E starts with D followed by ".". For example, the descriptor done matches done.state.a but not donex. The descriptor x.y matches x.y.z but matches neither x.yz nor x.
- A timer reservation: the transition is exactly the transition that the reservation refers to.
- Eventless: the transition is an eventless transition.
Selection is done by the following procedure.
1. Take each atomic state in the configuration, one at a time in document order, as a, and perform the following search for a. Examine states s in the order a, the parent of a, its parent, ..., up to the top-level state; for each s, look at the transitions whose source is s in order, evaluate the guard of each transition that matches the trigger, select for a the first transition whose guard is true, and end the search for a. If none is found for any s, nothing is selected for a. The guard of a transition that does not match the trigger is not evaluated.
2. Arrange the transitions selected in step 1 in the order of a. If the same transition appears two or more times, keep only the first occurrence.
3. Examine the transitions of the list from step 2 from front to back: remove a transition if its exit set has a state in common with the exit set of any transition already decided to be kept, and keep it otherwise.
The list of transitions remaining in this way (possibly empty) is called the "selected transitions". In step 1, the guard of the same transition may be evaluated more than once, and each time an evaluation error occurs, error.execution is added to the internal queue again.

== 9. Microsteps ==
Executing non-empty selected transitions is called a "microstep". The "display name" of a trigger is defined as follows: for an event, its name if the value is 0, and otherwise the name, "=" and the value concatenated (for example coin=50, coin=-10); for a timer reservation, "after(<K>)@<source>" (K and the source are those of the transition that the reservation refers to); and for eventless, "always". A microstep is performed by the following procedure.
1. Compute the set X that is the union of the exit sets of all selected transitions.
2. Record history. For each history state h that is a child of a state s in X, record as the value of h the following states arranged in document order (any previous value is discarded): if deep is written on the line that defines h, the atomic states in the configuration that are descendants of s; if shallow is written, the child states of s that are in the configuration. This recording is done on the configuration before it is changed.
3. Compute the entry set Y. First, for each selected transition that is not an internal transition, and for each state x of its effective targets, add to Y x and those ancestors of x that are descendants of the scope of that transition. Here the effective targets are determined by the history values after the recording in step 2, and the scope is the one used in step 1. Next, repeat the following until no new state is added to Y: add to Y all child states of every parallel state in Y, and, for every compound state in Y none of whose child states is in Y, add its initial child state to Y.
4. If trace is on, output "[t=<time>] <display name> (<source list>): exit <exit list>; enter <entry list>". The source list is the sources of the selected transitions, in the order of the selected transitions; the exit list is X in reverse document order; the entry list is Y in document order.
5. Exit: take each state of X, one at a time in reverse document order, as s; execute the exit action lists of s in order, remove s from the configuration, add "current time - entry time of s" to the dwell time of s, and remove from the reservation list all timer reservations that refer to a transition whose source is s.
6. For each selected transition in order, execute its action list and add 1 to the transition count of its source.
7. Entry: take each state of Y, one at a time in document order, as s, and do the following a to d.
  a. Add s to the configuration, add 1 to the entry count of s, and set the entry time of s to the current time.
  b. For each timer transition whose source is s, in transition order, create a timer reservation that refers to that transition, with due time "current time + K", and add it to the reservation list.
  c. Execute the entry action lists of s in order.
  d. If s is a final state, let p be the parent of s, and append to the end of the internal queue an event with name "done.state.<p>" and value 0. Furthermore, if the parent g of p is a parallel state and all child states of g are "complete", append to the end of the internal queue an event with name "done.state.<g>" and value 0. A state r is complete if, when r is a compound state, a final state that is a child of r is in the configuration, and, when r is a parallel state, all child states of r are complete. An atomic state is not complete. Completeness is determined on the configuration at that moment.

== 10. Macrosteps ==
A "macrostep" is the following processing, started from one of: the start, one external event, or one reservation.
1. Add 1 to the number of macrosteps. Let c be the number of microsteps executed within this macrostep, initially 0. Below, "perform a microstep" means: if c is 1000, output "LIVELOCK t=<time>", halt, and end this macrostep immediately (events remaining in the internal queue are not processed either). If c is not 1000, add 1 to both c and the number of microsteps, and then perform the microstep of section 9.
2. Depending on the starting point, do the following.
  - Start: set the current value to 0. Starting from the set containing only the initial child state of the root, perform the repetition in the second half of step 3 of section 9 to compute the entry set Y, and enter the states of Y in the same way as step 7 of section 9. This is not a microstep, and no trace is output.
  - External event: set the current value to the value of that event, select transitions with that event as the trigger, and if the selected transitions are not empty, perform a microstep.
  - Timer reservation: set the current value to 0, select transitions with that reservation as the trigger, and if the selected transitions are not empty, perform a microstep.
  - Send reservation: treat the event held by the reservation as an external event and do the same as for an external event above.
3. Repeat the following a to c.
  a. Set the current value to 0 and select transitions with eventless as the trigger. If the selected transitions are not empty, perform a microstep and go back to a.
  b. If the internal queue is empty, end the macrostep.
  c. Take out the event at the front of the internal queue, set the current value to the value of that event, and select transitions with that event as the trigger. If the selected transitions are not empty, perform a microstep. Then go back to a.
For a valid chart, after outputting the warnings of section 3, perform one macrostep started from the start.

== 11. Script commands ==
Execute the script lines one at a time in order. Once halted, the remaining script lines are not executed (nothing is output and nothing is changed).
- event EVENT and event EVENT VALUE: perform a macrostep started from an external event with name EVENT and value VALUE (0 if there is no VALUE).
- tick N: let F be the time plus N, and repeat the following. If halted, end the repetition. If the reservation list has no reservation with a due time of at most F, end the repetition. Otherwise, remove from the reservation list the one with the smallest due time among them (for equal due times, the one with the smallest creation number), change the time to the due time of that reservation, and perform a macrostep started from that reservation. When the repetition ends, if not halted, change the time to F. Reservations created during the repetition are also processed within the same tick if their due time is at most F.
- set NAME VALUE: if the variable NAME is declared, change its value to VALUE. Nothing is output and no macrostep is performed. If it is not declared, change nothing and output "error: unknown variable <NAME>".
- trace on: turn trace on. trace off: turn trace off.
- eval EXPR: first examine the references in EXPR from left to right; if there is an undeclared variable name (except _data), output "error: unknown variable <that name>", and if there is an in(S) referring to an undefined state, output "error: unknown state <S>", for whichever is found first. If there is neither, evaluate EXPR with the current value set to 0; if an evaluation error occurs, output "error: division by zero", and otherwise output "<EXPR> -> <value>". Here <EXPR> is exactly the EXPR string as written in the input. eval does not add events to the internal queue.
- dump: output the following lines in order.
  1. "dump t=<time>".
  2. For each state in the configuration, in document order, a line consisting of 2 * (the depth of that state) spaces followed by the state name.
  3. For each declared variable, in name order of the variable names, "  var <NAME> = <value>".
  4. For each history state whose value is recorded, in document order, "  history <ID> = <recorded list>".
  5. For each reservation in the reservation list, in increasing order of due time (for equal due times, in increasing order of creation number): for a timer, "  timer <due time> after(<K>)@<source>"; for a send, "  send <due time> <event name> <event value>". K and the source are those of the transition that the timer refers to.

== 12. Statistics ==
When the END line is reached (even if halted), output "end t=<time> macrosteps=<number of macrosteps> microsteps=<number of microsteps>", followed, for each state that is not a history state, in document order, by "  <ID> entered=<entry count> taken=<transition count> time=<total dwell time>". The entry count is the number of times the state was entered (step 7a of section 9), and the transition count is the number of times a transition whose source is the state was executed (step 6 of section 9). The total dwell time is the dwell time of the state (step 5 of section 9) if the state is not in the configuration, and that dwell time plus "current time - entry time of the state" if it is.

[Output format]
The output of each chart consists of the lines defined in [Processing], output in the order of the charts. Within one chart, lines are output in the order described in [Processing].
All output consists of ASCII characters, and every line ends with a newline (LF). No line has trailing spaces, and no empty lines are output. The only lines that start with spaces are the second and later lines of dump, the second and later lines of the statistics, and some of the lines output by log.
A space within a string is a single space unless otherwise specified.

[Constraints]
- 1 <= T <= 20, and the whole input has at most 5000 lines.
- Each chart has at most 120 definition lines and at most 300 script lines.
- Each chart defines at most 40 states and declares at most 20 variables. One ACTIONS has at most 10 actions, and one TRIGGER has at most 5 event descriptors.
- A valid chart has at least one top-level state.
- In an action of the form log STRING, the text between the opening and closing double quotes of STRING has at least 1 character, and its last character is not a space.
- The absolute value of every value that appears in expression evaluation (including variable values, event values and intermediate values of computations) is always at most 1000000000.
- In the run of one chart, at most 5000 reservations are created, at most 10000 events are added to the internal queue, and at most 10000 microsteps are executed.

[Example]
Input:
2
CHART bad
state a
state b c
on a go -> d
RUN
event go
END
CHART door
state closed initial locked
state locked closed
state unlocked closed
state opened
var opens 0
entry opened / opens = opens + 1; log "opened #" opens
on locked unlock [_data == 42] -> unlocked
on locked unlock / log "wrong key " _data
on unlocked open -> opened
on opened after 3 -> closed / log "auto close"
RUN
event unlock 7
event unlock 42
trace on
event open
tick 5
dump
END

Output:
chart bad
error line 4: unknown state c
error line 5: unknown state d
chart door
wrong key 7
[t=0] open (unlocked): exit unlocked,closed; enter opened
opened #1
[t=3] after(3)@opened (opened): exit opened; enter closed,locked
auto close
dump t=5
  closed
    locked
  var opens = 1
end t=5 macrosteps=5 microsteps=4
  closed entered=2 taken=0 time=2
  locked entered=2 taken=2 time=2
  unlocked entered=1 taken=1 time=0
  opened entered=1 taken=1 time=3
