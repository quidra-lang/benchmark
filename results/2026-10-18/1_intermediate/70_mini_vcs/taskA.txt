[Overview]
Write a program that simulates a small version control system similar to git. The program holds in memory a working tree (the files being worked on), an index (the content to include in the next commit), the commit history, branches and tags, HEAD, and a stash (a place where work in progress is set aside temporarily). It executes the commands read from standard input one at a time, in order from the first, and writes the results to standard output. A file consists only of a path and a one-line content. The features covered are: staging and committing changes, displaying status, history and differences, branches and tags, switching HEAD, fast-forward merges and three-way merges with conflict resolution, reset, undoing a commit (REVERT) and applying a commit (CHERRYPICK), rebase, stash, showing the commit that last changed a path (BLAME), graph display, describing a commit relative to tags (DESCRIBE), and deleting unreachable commits.

[Input format]
The input consists of several lines, each containing one command, and the last line is a line consisting only of the four characters "EXIT". Each line is a command name followed by zero or more arguments, separated by single spaces. No line has spaces at its beginning or end, and there are no empty lines. However, the text of WRITE and the message of COMMIT and AMEND are each a single argument that may contain spaces (see the description below).
The command syntax is as follows ([ ] marks an optional part).

  WRITE path text
  REMOVE path
  ADD path
  ADD ALL
  RM path
  UNSTAGE path
  RESTORE path [rev]
  IGNORE pattern
  COMMIT message
  AMEND message
  STATUS
  LS [rev]
  CAT path [rev]
  DIFF
  DIFF STAGED
  DIFF rev1 rev2
  LOG [n]
  SHOW [rev]
  BLAME path
  BRANCH name [rev]
  BRANCH -d name
  BRANCHES
  TAG name [rev]
  TAG -d name
  TAGS
  SWITCH name
  DETACH rev
  MERGE rev
  MERGEBASE rev1 rev2
  REBASE rev
  RESET mode rev
  REVERT rev
  CHERRYPICK rev
  STASH
  STASH POP
  STASH DROP
  STASH LIST
  GRAPH
  DESCRIBE [rev]
  GC
  EXIT

The arguments are as follows.
- path is a string of 1 to 16 characters consisting of lowercase letters (a to z), digits (0 to 9), ".", "_" and "/".
- pattern is a string of 1 to 16 characters consisting of the characters allowed in path and "*" and "?".
- name (a branch name or a tag name) is a string of 1 to 12 characters consisting of lowercase letters, digits and "-", whose first character is a lowercase letter.
- rev (a revision) is either an "anchor" alone, or an anchor immediately followed by "~" and an integer k (examples: HEAD~2, main~1). The anchor is one of: "HEAD", a string of the same form as name, or a string of 8 characters consisting of digits and the lowercase letters a to f. rev1 and rev2 have the same form as rev.
- k and n are integers from 1 to 99, written without extra leading zeros.
- mode is one of SOFT, MIXED and HARD.
- text (the file content) is the entire part of a WRITE line after the second space. message (the commit message) is the entire part of a COMMIT or AMEND line after the first space. Both consist of printable ASCII characters (codes 32 to 126), and their first and last characters are not spaces. text is 1 to 30 characters long, and message is 1 to 40 characters long.
It is guaranteed that every line follows these formats and [Constraints]. However, the branches, tags, commits, paths, etc. given as arguments do not necessarily exist (how this is handled is described in [Processing]).

[Processing]
Execute the commands one at a time in input order. When EXIT is read, terminate the program without printing anything.

=== Trees ===
A "tree" maps each of some paths to a content (a one-line string). The same path never appears twice in one tree. When tree T contains path p, the content of p is written T[p]. A tree that contains no paths is called the "empty tree".
Trees A and B "agree" on a path p when neither A nor B contains p, or both contain p and A[p] equals B[p]. When they agree on every path, A and B are "equal". The set of all paths on which A and B do not agree is called the "differing paths of A and B".
To "make path p of tree X match tree Y" means: if Y contains p, set X[p] to Y[p] (adding p if X does not contain it); if Y does not contain p, remove p from X (doing nothing if X does not contain p).
The "ascending order" of strings is the lexicographic order comparing character codes (if one string is a prefix of the other, the shorter one comes first). Paths, branch names and tag names are always sorted in this ascending order.

=== State ===
The program holds the following state.
- A collection of commits. Each commit has an ID (an 8-character string), a sequence number (an integer >= 0), a parent list (a list of 0 to 2 commits), a tree, and a message. The first element of the parent list is called the "first parent", and the second the "second parent". The contents of a commit never change after it is created.
- A collection of branches and a collection of tags. Each is a collection of pairs of a name and one commit; names are unique among branches and unique among tags (a branch and a tag with the same name can exist at the same time). The commit of a pair is called "the commit the branch (tag) points to".
- HEAD. HEAD is either "attached" to some branch, or "detached", pointing directly to some commit. When HEAD is attached to branch b, the commit b points to is called the "HEAD commit"; when it is detached, the commit HEAD points to directly is called the "HEAD commit". The tree of the HEAD commit is written H. To "move HEAD to commit X" means: if HEAD is attached to a branch, change that branch to point to X (HEAD stays attached to that branch); if it is detached, change HEAD to point directly to X.
- The working tree W and the index I (both are trees).
- The set of conflict paths C.
- The operation in progress P. P is either "none" or a pair of a kind (one of merge, revert and cherry-pick) and a commit.
- The stash list. Each entry consists of a label (a string), a base commit, and a saved tree. The entries of the list are called stash@{0}, stash@{1}, ... in order from the front.
- The list of ignore patterns.
In the initial state there is only one commit, with sequence number 0, no parents, the empty tree and the message "init" (called the "root commit"); the only branch is main, which points to the root commit, and HEAD is attached to main. There are no tags, no stash entries and no ignore patterns; W, I and C are empty, and P is none.

=== Creating and recording commits ===
To "create a commit" from a given parent list, tree and message, make a new commit with them and add it to the collection of commits. The sequence number s of the new commit is the number of commits created so far (counting the root commit and also commits deleted by GC; that is, the commit created right after the root commit has sequence number 1, and the numbers increase by 1 after that). The ID is determined as follows. The "canonical text" is the string obtained by taking the following lines in this order, appending a newline character (code 10) to the end of each line, and concatenating them.
  commit <s> (<s> is the sequence number in decimal without extra leading zeros)
  parent <parent ID> (one line per parent, in parent-list order)
  file <path> <content> (one line per path contained in the tree, in ascending order of paths)
  message <message>
Look at the characters of the canonical text in order from the first; starting with h=0, for each character with character code c, replace h with (h*131+c) mod 2147483647. The ID is the final h written in hexadecimal and padded on the left with 0 to 8 characters (10 to 15 are written as the lowercase letters a to f). For example, the canonical text of the root commit is the two lines "commit 0" and "message init" (22 characters including the newline characters), and its ID is 649fbe66. The input is constructed so that the ID of every created commit differs from the IDs of all previously created commits.
To "record a commit" from a given parent list, tree and message, create a commit, move HEAD to that commit, and print the following "commit report line".
  [<location> <ID>] <message> (<A> added, <M> modified, <D> deleted)
The location is the branch name if HEAD is attached to a branch, or "detached HEAD" if it is detached. With the tree of the first parent as the old tree and the tree of the new commit as the new tree, A, M and D are the number of paths not contained in the old tree but contained in the new tree, the number of paths contained in both with different contents, and the number of paths contained in the old tree but not in the new tree (a recorded commit always has a parent). The tree of a commit is a copy of the given tree; changing I etc. later does not change the tree of the commit.

=== Resolving revisions ===
To resolve rev and obtain one commit, first examine the anchor in the following order. If it is "HEAD", the result is the HEAD commit. Otherwise, if there is a branch with the same name as the anchor, it is the commit that branch points to. Otherwise, if there is a tag with the same name, it is the commit that tag points to. Otherwise, if the collection of commits contains a commit whose ID is the anchor, it is that commit. If none of these applies, the resolution fails. Next, if "~k" is attached, replace the commit with its first parent, k times. If at some point this would follow the first parent of a commit that has no parents, the resolution fails.
When the resolution fails, print "error: unknown revision '<rev>'" (<rev> is the argument string exactly as written) and do nothing else for that command.

=== Ancestors, distance, merge base ===
A commit that can be reached from commit X by repeating a move to a parent (either the first or the second parent) zero or more times is called an "ancestor" of X. X itself is also an ancestor of X. For an ancestor Y of X, the "distance" from X to Y is the minimum number of moves needed to reach Y from X.
The "merge base" of two commits X and Y is determined as follows. A commit that is an ancestor of both X and Y is called a "common ancestor" (the root commit is always a common ancestor). A common ancestor Z that is not an ancestor of any common ancestor other than Z is a "candidate". Among the candidates, choose those for which "the larger of the distance from X to Z and the distance from Y to Z" is smallest; if there are several, the one among them with the largest sequence number is the merge base.

=== Common display formats ===
- The "summary line" of commit X is "<ID of X> <message of X>". However, if one or more references point to X, insert " (<reference list>)" between the ID and the message (example: "1a2b3c4d (HEAD -> main, dev, tag: v1) Fix bug"). The reference list is the items below, in the order 1, 2, 3, joined with ", " (a comma and one space).
  1. If HEAD is detached and points directly to X, "HEAD". If HEAD is attached to branch b and b points to X, "HEAD -> <b>" (<b> is the branch name).
  2. The names of the branches pointing to X (excluding the b mentioned in 1), in ascending order.
  3. For each tag pointing to X, "tag: <tag name>", in ascending order of tag names.
- The "change list" from tree A to tree B is the output of one line for each differing path of A and B, in ascending order of paths, as follows. If there are no differing paths, only the single line "(no changes)" is printed.
  When A does not contain p (B does): "A <p>: <B[p]>"
  When B does not contain p (A does): "D <p>: <A[p]>"
  When both A and B contain p: "M <p>: <A[p]> -> <B[p]>"

=== Common checks and operations ===
In the description of each command, error conditions are listed in the order in which they are checked. When an error occurs, print only that error's single line and do nothing else for that command (the state does not change at all). A failed revision resolution is also an error.
- "In-progress check": if P is not none, it is an error with "error: <kind> in progress" (<kind> is the kind of P).
- "Uncommitted check": if I and H are not equal, or W and I do not agree on some path contained in I, it is an error with "error: uncommitted changes". When this condition holds, we say "there are uncommitted changes". Paths not contained in I and contained only in W do not matter for this check.
- "Overwrite check" (given a set of paths S): examine the paths of S in ascending order; if there is a path on which I and H do not agree, or W and H do not agree, it is an error with "error: local changes to '<p>' would be overwritten" for the first such path p found.
- "Switching to tree T": with S the set of differing paths of H and T, perform the overwrite check; if it is not an error, make each path of S in I and in W match T. For paths not in S, neither I nor W is changed (so uncommitted changes on those paths remain as they are).

=== Three-way merge ===
The "three-way merge" of a base tree B, our tree O and their tree T computes a result tree M and a set of conflict paths K by deciding, for each path p contained in at least one of B, O and T, as follows. M and K are initially empty.
  1. If T and B agree on p, or O and T agree on p, make path p of M match O (if O contains p, M[p]=O[p]; otherwise M does not contain p).
  2. Otherwise, if O and B agree on p, make path p of M match T.
  3. Otherwise, p is a conflict. Add p to K and make path p of M match O. Also, the "conflict content" of p is "<<<<<<< <o> ======= <t> >>>>>>>". <o> is O[p] if O contains p, and "(deleted)" otherwise; <t> is determined in the same way for T.

=== Apply procedure ===
MERGE (when it performs a three-way merge), REVERT and CHERRYPICK determine a base tree B, their tree T, a kind, a target commit X, a message and a parent list, and perform the following "apply procedure".
  1. Perform the three-way merge of B, H and T (our tree is H) and obtain M and K.
  2. Perform the overwrite check on the union of the set of differing paths of H and M and the set K.
  3. If the kind is merge, print "Merge base <ID>" (<ID> is the ID of the merge base computed by MERGE).
  4. If the kind is not merge, K is empty and M equals H, print "nothing to commit" and finish (the state does not change).
  5. For each differing path of H and M, make that path of I and W match M.
  6. If K is empty, record a commit with the determined parent list, M and the message, and finish.
  7. If K is not empty, for each path p of K in ascending order, set W[p] to the conflict content of p (adding it if W does not contain p) and print "CONFLICT <p>". Next, make C equal to K and set P to (kind, X). Finally, print "Automatic merge failed; fix conflicts and then commit the result." if the kind is merge, "error: could not revert <ID of X>" if it is revert, or "error: could not apply <ID of X>" if it is cherry-pick (this last line is not an error line; the state changes as described above).

=== Ignore patterns ===
In a pattern, "*" matches any string of zero or more characters (it may contain "/"), "?" matches any single character, and every other character matches itself; a path matches a pattern when the whole pattern matches the whole path. For example, "*.log" matches both "a.log" and "logs/b.log", and "tmp?.txt" matches "tmp1.txt" but not "tmp12.txt". When path p matches any pattern in the list of ignore patterns and is contained in neither I nor C, p is called an "ignored path".

=== Commands ===
WRITE path text
Set W[path] to text (adding path if W does not contain it). Print nothing.

REMOVE path
If W does not contain path, it is an error with "error: no such file '<path>'". Otherwise, remove path from W. Print nothing.

ADD path
1. If W contains path and path is an ignored path, it is an error with "error: path '<path>' is ignored".
2. If none of W, I and C contains path, it is an error with "error: pathspec '<path>' did not match any files".
3. Make path of I match W, and remove path from C (doing nothing if it is not contained). Print nothing.

ADD ALL
For each path contained in at least one of W and I that is not an ignored path, make that path of I match W (whether a path is ignored is decided on the state before this command is executed). Then make C empty. Print nothing.

RM path
If I does not contain path, it is an error with "error: pathspec '<path>' did not match any files". Otherwise, remove path from I, W and C (if W does not contain path, W does not change). Print nothing.

UNSTAGE path
If neither I nor H contains path, it is an error with "error: pathspec '<path>' did not match any files". Otherwise, make path of I match H. W and C are not changed. Print nothing.

RESTORE path
If I does not contain path, it is an error with "error: pathspec '<path>' did not match any files". Otherwise, set W[path] to I[path] (adding path if W does not contain it). I and C are not changed. Print nothing.

RESTORE path rev
1. Resolve rev to obtain commit X.
2. If the tree of X does not contain path, it is an error with "error: path '<path>' does not exist in '<rev>'" (<rev> is the argument string exactly as written).
3. Set both I[path] and W[path] to the content of path in the tree of X (adding it where it is not contained), and remove path from C. Print nothing.

IGNORE pattern
Append pattern to the end of the list of ignore patterns. Print nothing.

COMMIT message
1. If C is not empty, it is an error with "error: unresolved conflicts".
2. If the kind of P is merge, record a commit with the parent list (HEAD commit, commit of P), I and message, and set P to none. In this case I and H may be equal.
3. Otherwise, if I and H are equal, print "nothing to commit" (the state does not change, and P also stays as it is).
4. Otherwise, record a commit with the parent list (HEAD commit), I and message, and set P to none.

AMEND message
1. In-progress check.
2. If the HEAD commit has no parents, it is an error with "error: cannot amend the root commit".
3. Record a commit with the same parent list as the HEAD commit (in the same order), I and message. The original HEAD commit is not deleted and remains. I may equal H, and I may equal the tree of the first parent.

STATUS
First, print "On branch <branch name>" if HEAD is attached to a branch, or "HEAD detached at <ID of the HEAD commit>" if it is detached. If P is not none, then print "Merging <ID>" if the kind of P is merge, "Reverting <ID>" if it is revert, or "Cherry-picking <ID>" if it is cherry-pick (<ID> is the ID of the commit of P).
Next, examine each path p contained in at least one of H, I, W and C in ascending order, and print the following lines.
- When p is contained in C: print "UU <p>".
- Otherwise, when I contains p: the first character x is "A" if H does not contain p, "M" if it does and H[p] and I[p] differ, and "." if they are equal; the second character y is "D" if W does not contain p, "M" if it does and W[p] and I[p] differ, and "." if they are equal. Print "<x><y> <p>" unless both x and y are ".".
- Otherwise (I does not contain p): if H contains p, print "D. <p>". Furthermore, if W contains p and p is not an ignored path, print "?? <p>" (when both are printed, they come in this order).
If no line about a path was printed, print "nothing to commit, working tree clean" instead.

LS [rev]
The target is W if rev is absent, or the tree of the commit obtained by resolving rev if it is present. For each path of the target tree, in ascending order of paths, print "<path> <content>" on its own line. If the target tree is empty, print "(empty)".

CAT path [rev]
When rev is absent: if W does not contain path, it is an error with "error: no such file '<path>'". If it does, print W[path].
When rev is present: resolve rev to obtain commit X. If the tree of X does not contain path, it is an error with "error: path '<path>' does not exist in '<rev>'". If it does, print that content.

DIFF
Let W' be the tree obtained from W by removing the paths not contained in I, and print the change list from I to W' (paths not contained in I are not compared).

DIFF STAGED
Print the change list from H to I.

DIFF rev1 rev2
Resolve rev1 and then rev2 (if resolving rev1 fails, rev2 is not resolved), and print the change list from the tree of the rev1 commit to the tree of the rev2 commit.

LOG [n]
Starting from the HEAD commit, repeatedly print the summary line of the current commit and then move to its first parent. Stop when the summary line of a commit that has no parents has been printed, or when n is given and n lines have been printed.

SHOW [rev]
Resolve rev (HEAD when omitted) to obtain commit X. Print "commit <summary line of X>" and "parents: <parent IDs>" (<parent IDs> is the IDs of the parents of X in parent-list order, separated by single spaces; if X has no parents, "parents: none"), then print the change list from the tree of the first parent of X (the empty tree if X has no parents) to the tree of X.

BLAME path
1. If H does not contain path, it is an error with "error: path '<path>' does not exist in 'HEAD'".
2. Let v be H[path] and Y be the HEAD commit. While Y has a parent, the tree of the first parent of Y contains path, and its content equals v, replace Y with the first parent of Y. Then print "<ID of Y> (<message of Y>) <v>".

BRANCH name [rev]
1. If a branch named name exists, it is an error with "error: branch '<name>' already exists".
2. Resolve rev (HEAD when omitted) to obtain commit X.
3. Create branch name pointing to X and print "Created branch <name> at <ID of X>". HEAD does not change.

BRANCH -d name
1. If no branch named name exists, it is an error with "error: no such branch '<name>'".
2. If HEAD is attached to name, it is an error with "error: cannot delete current branch '<name>'".
3. If the commit name points to is not an ancestor of the HEAD commit, it is an error with "error: branch '<name>' is not fully merged".
4. Delete branch name and print "Deleted branch <name> (was <ID>)" (<ID> is the ID of the commit name pointed to).

BRANCHES
If HEAD is detached, first print "* (HEAD detached at <ID of the HEAD commit>)". Then, for each branch in ascending order of names, print "<mark> <name> <ID> <message>". <ID> and <message> are those of the commit the branch points to. <mark> is "*" if HEAD is attached to that branch, and a single space otherwise (so such a line starts with two spaces).

TAG name [rev]
1. If a tag named name exists, it is an error with "error: tag '<name>' already exists".
2. Resolve rev (HEAD when omitted) to obtain commit X.
3. Create tag name pointing to X and print "Created tag <name> at <ID of X>".

TAG -d name
If no tag named name exists, it is an error with "error: no such tag '<name>'". If it exists, delete it and print "Deleted tag <name> (was <ID>)" (<ID> is the ID of the commit name pointed to).

TAGS
For each tag in ascending order of names, print "<name> <ID> <message>" (<ID> and <message> are those of the commit the tag points to). If there are no tags, print "(no tags)".

SWITCH name
1. If no branch named name exists, it is an error with "error: no such branch '<name>'".
2. If HEAD is attached to name, print "Already on '<name>'" and finish.
3. In-progress check.
4. Switching to the tree of the commit name points to (the overwrite check may cause an error).
5. Attach HEAD to name and print "Switched to branch '<name>'".

DETACH rev
1. Resolve rev to obtain commit X.
2. In-progress check.
3. Switching to the tree of X.
4. Detach HEAD so that it points directly to X, and print "HEAD is now at <ID of X> <message of X>".

MERGE rev
1. Resolve rev to obtain commit X.
2. In-progress check. Below, let Y be the HEAD commit.
3. If X is an ancestor of Y, print "Already up to date" and finish.
4. If Y is an ancestor of X (fast-forward), perform switching to the tree of X, move HEAD to X, print "Fast-forward <ID of Y>..<ID of X>" and finish.
5. Uncommitted check.
6. Let Z be the merge base of Y and X. Perform the apply procedure with the tree of Z as the base tree, the tree of X as their tree, kind merge, target commit X, message "Merge <rev>" (<rev> is the argument string exactly as written), and parent list (Y, X).

MERGEBASE rev1 rev2
Resolve rev1 and then rev2 (if resolving rev1 fails, rev2 is not resolved), and print the ID of the merge base of the two commits obtained.

REBASE rev
1. Resolve rev to obtain commit U.
2. In-progress check.
3. If U is an ancestor of the HEAD commit, print "Already up to date" and finish.
4. Uncommitted check.
5. Build a list of commits L as follows. Let Z be the HEAD commit; while Z is not an ancestor of U, append Z to the end of L and replace Z with the first parent of Z. Then reverse L (older commits come first). Since the root commit is an ancestor of U, every commit in L has a parent. L may be empty.
6. Let R be the tree of U. For each commit Z of L in order, perform the three-way merge with the tree of the first parent of Z as the base tree, R as our tree and the tree of Z as their tree, and obtain M and K. If K is not empty, it is an error with "error: could not rebase <ID of Z>: conflict in '<p>'" (<p> is the first path of K in ascending order) (no commit is created and the state does not change). If K is empty: if M and R are equal, mark Z as "skip"; otherwise mark Z as "pick", record M with Z, and set R to M.
7. Perform switching to R (the overwrite check may cause an error; in that case, too, no commit is created).
8. Let T be U, and for each commit Z of L in order, do the following. If Z is pick, create a commit with the parent list (T), the M recorded with Z and the message of Z (HEAD is not moved here, and no commit report line is printed); with N the created commit, print "pick <ID of Z> -> <ID of N> <message of Z>" and set T to N. If Z is skip, print "skip <ID of Z> <message of Z>".
9. Move HEAD to T and print "HEAD is now at <ID of T> <message of T>".

RESET mode rev
1. Resolve rev to obtain commit X. Let T be the tree of X.
2. If mode is HARD, for each path contained in at least one of I, T and C, make that path of W match T (I and C are those before this command is executed). W is not changed for other paths.
3. If mode is MIXED or HARD, make I equal to T.
4. Move HEAD to X, make C empty, set P to none, and print "HEAD is now at <ID of X> <message of X>".
RESET does not perform the in-progress check (it can also be used to abort an operation in progress).

REVERT rev
1. Resolve rev to obtain commit X.
2. In-progress check.
3. Uncommitted check.
4. Let Q be the tree of the first parent of X (the empty tree if X has no parents). Perform the apply procedure with the tree of X as the base tree, Q as their tree, kind revert, target commit X, message "Revert "<message of X>"", and parent list (HEAD commit).

CHERRYPICK rev
1. Resolve rev to obtain commit X.
2. In-progress check.
3. Uncommitted check.
4. Determine Q in the same way as REVERT. Perform the apply procedure with Q as the base tree, the tree of X as their tree, kind cherry-pick, target commit X, the message of X as the message, and parent list (HEAD commit).

STASH
1. In-progress check.
2. If there are no uncommitted changes, print "No local changes to save" and finish.
3. Let S be the tree consisting only of the paths contained in at least one of I and H that are also contained in W, with the content of each path the same as in W.
4. For each path contained in at least one of I and H, make that path of W match H, and then make I equal to H. W is not changed for other paths.
5. Let the label be "WIP on <location>: <ID of the HEAD commit> <message of the HEAD commit>" (<location> is the branch name if HEAD is attached to a branch, or "(no branch)" if it is detached), and add an entry consisting of this label, the base commit (the HEAD commit) and the saved tree S to the front of the stash list.
6. Print "Saved stash@{0}: <label>".

STASH POP
1. If the stash list is empty, it is an error with "error: no stash entries".
2. In-progress check.
3. Uncommitted check.
4. Let L be the label, Z the base commit and S the saved tree of the front entry. Perform the three-way merge with the tree of Z as the base tree, H as our tree and S as their tree, and obtain M and K. If K is not empty, it is an error with "error: stash conflict in '<p>'" (<p> is the first path of K in ascending order).
5. Perform the overwrite check on the set of differing paths of H and M.
6. For each differing path of H and M, make that path of W match M (I is not changed). Remove the front entry from the list, print "Restored stash@{0}: <L>", and then print the change list from H to M.

STASH DROP
If the stash list is empty, it is an error with "error: no stash entries". Otherwise, remove the front entry from the list and print "Dropped stash@{0}: <label of that entry>".

STASH LIST
For each entry of the stash list, in order from the front, print "stash@{<i>}: <label>" (<i> is the position counted from 0). If the list is empty, print "(no stash entries)".

GRAPH
A commit that is an ancestor of the HEAD commit, of a commit some branch points to, or of a commit some tag points to is called a "reachable commit". Process the reachable commits one at a time in decreasing order of sequence number, printing one line for each (every commit has a larger sequence number than its parents, so it is processed before its parents). The processing uses a list of "lanes". Each lane holds one commit, and the list of lanes is initially empty. Commit X is processed as follows.
  1. If no lane holds X, append a lane holding X to the end of the list.
  2. Let k be the position of the frontmost lane holding X.
  3. The symbol of each lane is "*" for the lane at position k, "/" for any other lane holding X, and "|" for all other lanes. Print one line consisting of the symbols in lane-list order separated by single spaces, followed by one space and the summary line of X.
  4. Remove from the list all lanes holding X other than the one at position k (they are all behind position k).
  5. If X has no parents, remove the lane at position k from the list. If it has parents, replace the commit held by the lane at position k with the first parent of X; furthermore, if X has a second parent and no lane in the list holds the second parent, insert a lane holding the second parent right after the lane at position k.

DESCRIBE [rev]
1. Resolve rev (HEAD when omitted) to obtain commit X.
2. If no tag points to an ancestor of X, it is an error with "error: no tag can describe '<ID of X>'".
3. Among the tags pointing to ancestors of X, choose the one with the smallest distance from X to the commit the tag points to; if there are several, choose the first in ascending order of tag names. If the distance is 0, print "<tag name>"; otherwise print "<tag name>-<distance>-g<ID of X>".

GC
Keep the commits that are ancestors of any of the following commits, and delete all other commits from the collection of commits: the HEAD commit, the commit each branch points to, the commit each tag points to, the base commit of each stash entry, and the commit of P (when P is not none). Then print "Removed unreachable commits: <number of deleted commits>". From then on, resolving a rev whose anchor is the ID of a deleted commit fails.

[Output format]
- For each command, print only the lines described in [Processing]. WRITE, REMOVE, ADD, RM, UNSTAGE, RESTORE and IGNORE print nothing except on errors.
- Numbers are written in decimal without extra leading zeros, and IDs are written as 8 characters consisting of digits and the lowercase letters a to f.
- The output consists only of ASCII characters, and every line ends with a newline character. No empty lines are printed. Spaces appear at the beginning of a line only in lines of BRANCHES, and never at the end of a line.
- The error lines are as follows (the parts in < > are replaced with the corresponding values).
  error: no such file '<path>'
  error: pathspec '<path>' did not match any files
  error: path '<path>' is ignored
  error: path '<path>' does not exist in '<rev>'
  error: unknown revision '<rev>'
  error: unresolved conflicts
  error: cannot amend the root commit
  error: branch '<name>' already exists
  error: no such branch '<name>'
  error: cannot delete current branch '<name>'
  error: branch '<name>' is not fully merged
  error: tag '<name>' already exists
  error: no such tag '<name>'
  error: <kind> in progress
  error: uncommitted changes
  error: local changes to '<path>' would be overwritten
  error: could not rebase <ID>: conflict in '<path>'
  error: stash conflict in '<path>'
  error: no stash entries
  error: no tag can describe '<ID>'
- In addition, "error: could not revert <ID>" and "error: could not apply <ID>" are lines printed after the CONFLICT lines when a conflict occurs in the apply procedure.

[Constraints]
- The number of input lines (including the EXIT line) is between 2 and 1000.
- The number of commits created (including the root commit) is at most 200.
- At any time, W, I, the tree of every commit and every saved tree each contain at most 50 paths.
- There are always at most 30 branches and at most 30 tags, always at most 10 stash entries, and at most 10 ignore patterns.
- The length of a file content, including conflict contents, is always at most 1000 characters. The length of a commit message (including those created as "Merge <rev>" or "Revert "<message>"") is always at most 200 characters.

[Example]
Input:
WRITE a.txt apple
WRITE b.txt banana
ADD ALL
COMMIT First
BRANCH dev
SWITCH dev
WRITE a.txt apricot
ADD a.txt
COMMIT Change a on dev
SWITCH main
WRITE a.txt avocado
WRITE c.txt cherry
ADD ALL
COMMIT Change a on main
MERGE dev
STATUS
CAT a.txt
WRITE a.txt apricot and avocado
ADD a.txt
COMMIT Merge dev
LOG
EXIT

Output:
[main 1afc7ab2] First (2 added, 0 modified, 0 deleted)
Created branch dev at 1afc7ab2
Switched to branch 'dev'
[dev 12b2e04c] Change a on dev (0 added, 1 modified, 0 deleted)
Switched to branch 'main'
[main 2e21e9a7] Change a on main (1 added, 1 modified, 0 deleted)
Merge base 1afc7ab2
CONFLICT a.txt
Automatic merge failed; fix conflicts and then commit the result.
On branch main
Merging 12b2e04c
UU a.txt
<<<<<<< avocado ======= apricot >>>>>>>
[main 4b7ae196] Merge dev (0 added, 1 modified, 0 deleted)
4b7ae196 (HEAD -> main) Merge dev
2e21e9a7 Change a on main
1afc7ab2 First
649fbe66 init

In this example, a.txt is changed to different contents on both main and dev, so a.txt conflicts in MERGE dev (the merge base is the "First" commit). c.txt, which was added only on the main side, does not conflict. The COMMIT after rewriting the conflict content and running ADD creates a commit with two parents (the first parent is "Change a on main" and the second parent is "Change a on dev"). Since LOG follows only first parents, the dev commit is not shown.
