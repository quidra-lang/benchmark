[Overview]
Write a program that manages requests and releases of resources by processes in a system where each resource type has a fixed number of instances. The program reads commands from standard input, executes them one at a time from the first, and writes the results to standard output. As countermeasures against deadlock, it covers avoidance by the banker's algorithm, prevention by resource ordering, detection by a detection algorithm, and recovery by forcibly terminating processes.

[Input format]
The first line contains the number of commands N, and each of the following N lines contains one command. Each line consists of a command name followed by zero or more arguments, separated by single spaces. There is no whitespace at the beginning or end of a line, and there are no empty lines. Command names and keyword arguments such as AVOID, ON and ALL are written in uppercase ASCII letters (except the kind of HISTORY and the snapshot name name). Integer arguments are unsigned decimal integers, and nonzero integers have no leading zeros.

The format of each command is as follows. id is an integer denoting a process number, v is a resource vector (zero or more integers separated by single spaces), k is an integer, and name is a snapshot name (a string consisting only of lowercase ASCII letters and digits).

TRACE ON, TRACE OFF

Every line of the input follows one of these formats. However, the number of integers in a resource vector v may differ from the number of resource types (how this is handled is defined in [Processing]). The first command is always RESOURCES.

[Processing]
* Terms and state
Let m be the number of resource types, and call the types, from the first, A, B, C, ... (uppercase ASCII letters in alphabetical order). A resource vector is a list of m resource counts in type order. For two resource vectors x and y, we write "x <= y" when the value of x is less than or equal to the value of y for every type, and otherwise (when the value of x is greater than the value of y for some type) we say that "x exceeds y". Sums and differences of resource vectors are taken per type. A resource vector whose values are all 0 is called the zero vector, and the sum of the m values of a resource vector is called the "sum" of that resource vector.

The state of the system consists of the following.
- The total Total and the available amount Available (both resource vectors).
- The set of existing processes. Each process has a process number (distinct from those of all other processes), a maximum demand Max and an allocation Allocation (both resource vectors), and a creation number (the command number of the command that created the process). The need Need of a process is the resource vector Max minus Allocation.
- The wait queue. It lists the requests that were not granted and are waiting, in the order in which they were added. Each request is a triple of a process, a request vector, and the command number at which it started waiting. A process that has a request in the wait queue is called a "blocked" process. A process has at most one request in the wait queue.
- The history. It records events such as grants and releases of resources in the order in which they occurred. Each event is a tuple of a command number, a kind (one of granted, blocked, unblocked, released, finished, aborted, cancelled), a process number, and a resource vector; an event of kind unblocked also has a waiting time.
Separately, there are four settings, the operating mode (initially AVOID), the recovery policy (initially ALLOC), tracing (initially OFF) and automatic detection (initially OFF), and a snapshot store (initially empty).
Command numbers are numbers assigned to the commands in order, with the command on the second line of the input numbered 1. The command number recorded with an event is the command number of the command being executed at that time.
At every point, Available plus the sum of the Allocation of all processes equals Total, and Allocation <= Max <= Total holds for each process.

* Safety check
Whether the current state is safe is determined by the following procedure. Let Work be a copy of Available and mark all processes as unfinished. While there is an unfinished process with Need <= Work, choose the one among them with the smallest process number, add its Allocation to Work, and mark it as finished. Stop when no process can be chosen. If all processes are finished, the state is safe, and the sequence of processes in the order in which they finished is called the safe sequence. If unfinished processes remain, the state is not safe, and the remaining processes are called "processes that cannot finish". If there are no processes at all, the state is safe.

* Detection algorithm
Let the request Request of each process be its request vector in the wait queue if the process is blocked, and the zero vector otherwise. Let Work be a copy of Available, mark the processes whose Allocation is the zero vector as finished from the start, and mark the remaining processes as unfinished. While there is an unfinished process with Request <= Work, choose the one among them with the smallest process number, add its Allocation to Work, and mark it as finished. The processes that remain unfinished when no process can be chosen are called deadlocked processes.

* Trace
When tracing is ON, the following checks output their intermediate steps: the safety checks performed by REQUEST, WHATIF, retries, CLAIM, REMOVE and SAFE, and the detection algorithm runs performed by DETECT, RECOVER (including RECOVER ALL) and automatic detection. The computations that MAXGRANT, SEQUENCES, DEFICIT and VICTIMS perform internally output nothing even when tracing is ON. When tracing is OFF, no check outputs intermediate steps.
The intermediate output of a safety check is as follows. First, at the start, output "[safety] start work=W" (W is the Work at the start); each time a process is marked finished, output "[safety] Pi can finish, work=W" (Pi is the chosen process, W is the Work after adding its Allocation); and finally, only when unfinished processes remain, output "[safety] stuck work=W remaining L" (W is the final Work, L is the list of unfinished processes).
The intermediate output of the detection algorithm has the same format, using "[detect]" instead of "[safety]". However, the start line is "[detect] start work=W idle L" (L is the list of those processes) if there are processes whose Allocation is the zero vector, and "[detect] start work=W" otherwise.

* Request decision
The handling when a process p requests a resource vector v is determined as follows. First, check the following conditions from top to bottom; the first one that applies is the reason for rejection.
1. p is blocked: the reason is "process Pp is blocked" (Pp is the name of p)
2. v is the zero vector: the reason is "zero vector"
3. v exceeds p's Need: the reason is "request exceeds need"
4. The operating mode is ORDER, p's Allocation is not the zero vector, and among the types for which the value of v is positive there is the last of the types for which p's Allocation is positive, or a type before it: the reason is "resource order violation" (for example, a process holding A and B can next request only types C and later)
If none of the conditions applies, whether to grant or block is decided as follows.
- If v exceeds Available, block. The reason for blocking is "insufficient resources".
- Otherwise, if the operating mode is AVOID, tentatively add v to p's Allocation and subtract v from Available, and perform the safety check in that state. If it is safe, grant; if it is not safe, undo the tentative allocation and block. The reason for blocking is "unsafe state".
- Otherwise, if the operating mode is DETECT or ORDER, grant.
When granting, add v to p's Allocation and subtract v from Available (WHATIF and MAXGRANT do not perform the allocation even when the request would be granted).

* Retry
Retrying the wait queue is the following process. Examine each request once, in order, from the head to the tail of the wait queue. For a request (process p, request vector v, command number s at which it started waiting), perform the latter part of the request decision, excluding the part that checks the reasons for rejection (that is, from the comparison of v with Available onward), in the state at that time. If it is granted, perform the allocation, remove the request from the wait queue, output "unblocked Pp V" (V is v), and record in the history an event of kind unblocked with vector v and waiting time (the current command number minus s). If it is blocked, the request stays at the same position in the wait queue, and nothing other than trace output is printed. Later requests are examined in the state that reflects the grants of earlier requests. The retry ends after one pass over the wait queue up to its tail.

* Errors
When a command results in an error, output the single line "error: MESSAGE" and do not change the state at all (record nothing in the history and do not retry). However, the intermediate output of safety checks performed to decide the error is printed before the error line if tracing is ON. In the description of each command, the error conditions are listed in the order in which they are checked, and only the error of the first condition that applies is output. The error conditions and MESSAGEs common to many commands are as follows.
- The number of integers in v is not m: "wrong vector length"
- No process with number id exists: "unknown process Pid"
- The process with number id is blocked: "process Pid is blocked"
- v is the zero vector: "zero vector"
Here Pid is the name of the process with number id; for example, if id is 7, the message is "unknown process P7". Below as well, Pid denotes the name of the process with number id, and V denotes v written in resource vector format.

* Processing of each command
RESOURCES t1 t2 ... tm
Let the number of resource types m be the number of integers given, set Total to (t1,t2,...,tm), and set Available to the same value as Total. Delete all existing processes and empty the wait queue and the history. The four settings and the snapshots are kept as they are. Output "resources T" (T is the new Total).

MODE x, POLICY x, TRACE x, AUTODETECT x
Set the operating mode, the recovery policy, tracing and automatic detection, respectively, to x, and output, respectively, "mode x", "policy x", "trace x", "autodetect x". Only the setting is changed; no retry or anything else is performed.

PROCESS id v
The error conditions are, in order: wrong vector length; a process with number id already exists (MESSAGE "duplicate process Pid"); v exceeds Total ("max exceeds total"). If there is no error, create a process whose Max is v, whose Allocation is the zero vector and whose creation number is the current command number, and output "process Pid max V". v may be the zero vector.

CLAIM id v
Changes the maximum demand of a process. The error conditions are, in order: wrong vector length; unknown process; process is blocked; Pid's Allocation exceeds v ("claim below allocation"); v exceeds Total ("max exceeds total"). After that, only when the operating mode is AVOID, tentatively set Pid's Max to v and perform the safety check; if it is not safe, restore Max and report an error ("claim makes state unsafe"). If there is no error, set Pid's Max to v, output "claim Pid max V", and then perform a retry.

ADD v
The error conditions are, in order: wrong vector length; zero vector. Add v to Total and Available, output "added V total T" (T is the Total after adding), and then perform a retry.

REMOVE v
The error conditions are, in order: wrong vector length; zero vector; v exceeds Available ("remove exceeds available"); subtracting v from Total makes some value 0 ("total must stay positive"); there is a process whose Max exceeds "Total minus v" ("max exceeds total"). After that, only when the operating mode is AVOID, perform the safety check in the state with v tentatively subtracted from Available; if it is not safe, restore it and report an error ("removal makes state unsafe"). If there is no error, subtract v from Total and Available and output "removed V total T" (T is the Total after subtracting). No retry is performed.

REQUEST id v
The error conditions are, in order: wrong vector length; unknown process; the reasons for rejection of the request decision. If there is a reason for rejection, it is an error whose MESSAGE is the reason string (for example "error: request exceeds need"). If there is no error, follow the request decision. When granted, output "granted Pid V" and record in the history an event of kind granted with vector v. When blocked, append the request (Pid, v, current command number) to the tail of the wait queue, output "blocked Pid V: R" (R is the reason for blocking), and record in the history an event of kind blocked with vector v. When blocked, in addition, if automatic detection is ON, then run the detection algorithm, and if there are deadlocked processes, output "deadlock detected: L" (L is the list of those processes) (output nothing if there are none).

WHATIF id v
Examines what would happen if the request were made. The error conditions are, in order: wrong vector length; unknown process. If there is no error, perform the request decision and output one of the following lines describing the result (the intermediate output of the safety check performed in the decision is printed before this line if tracing is ON). If there is a reason for rejection: "whatif Pid V: rejected (R)" (R is the reason for rejection). If it would be blocked: "whatif Pid V: blocked (R)" (R is the reason for blocking). If it would be granted: "whatif Pid V: granted, safe sequence L" (L is the safe sequence obtained by the safety check of the decision) when the operating mode is AVOID, and "whatif Pid V: granted" when it is DETECT or ORDER. The state, the wait queue and the history are not changed at all, and automatic detection is not performed.

RELEASE id v
The error conditions are, in order: wrong vector length; unknown process; process is blocked; zero vector; v exceeds Pid's Allocation ("release exceeds allocation"). Subtract v from Pid's Allocation, add v to Available, output "released Pid V", record in the history an event of kind released with vector v, and then perform a retry.

FINISH id
The process terminates normally. The error conditions are, in order: unknown process; process is blocked. Let U be Pid's Allocation; add U to Available, delete Pid, output "finished Pid released U" (U is written in resource vector format), record in the history an event of kind finished with vector U, and then perform a retry. U may be the zero vector.

ABORT id
Forcibly terminates the process. The only error condition is unknown process; a blocked process can also be aborted. If Pid is blocked, remove its request from the wait queue (nothing is output for this, and nothing is recorded in the history). Then, as with FINISH, add Pid's Allocation U to Available, delete Pid, output "aborted Pid released U", record in the history an event of kind aborted with vector U, and then perform a retry.

CANCEL id
Cancels a waiting request. The error conditions are, in order: unknown process; Pid is not blocked ("process Pid is not blocked"). Remove Pid's request (let R be its request vector) from the wait queue, output "cancelled Pid R" (R is written in resource vector format), and record in the history an event of kind cancelled with vector R. No retry is performed.

MAXGRANT id
The error conditions are, in order: unknown process; process is blocked. For each type, consider the resource vector whose value for that type is x and whose values for all other types are 0, and find the largest integer x, with 0 <= x <= (the value of Pid's Need for that type), such that x is 0 or a REQUEST of that resource vector made now would be granted (there is no reason for rejection and the decision grants it). The x for each type is found independently of the other types. Let X be the resource vector of the found x values in type order, and output "maxgrant Pid: X". The state is not changed.

SAFE
If there are no processes, output "safe: no processes" without performing the check. Otherwise perform the safety check, and output "safe: L" (L is the safe sequence) if the state is safe, or "unsafe: L cannot finish" (L is the list of processes that cannot finish) if it is not safe.

SEQUENCES k
If there are no processes, output "safe sequences: no processes". Otherwise, count the number C of safe permutations among the permutations that list every existing process exactly once. A permutation is safe if, with Work as a copy of Available, the following can be carried out up to the last process without encountering a process for which Need <= Work does not hold: starting from the first process of the permutation, if that process's Need <= Work, add its Allocation to Work and move on to the next process. Output "safe sequences: C", followed by the first min(k, C) safe permutations when the safe permutations are sorted in lexicographic order (compare process numbers from the first position; at the first differing position, the one with the smaller number comes first), one per line in that order, each written as a list of the processes of the permutation.

DEFICIT
For each type, find the smallest integer x such that performing the safety check in the state where only that type's value of Available is increased by x (the values of the other types are unchanged) gives a safe state. Search for x in the range from 0 to the sum of all processes' Need values for that type, inclusive; if there is no such x in that range, the result for that type is "-". Let D be the per-type results in type order, separated by ",", and enclosed as a whole in "(" and ")"; output "deficit: D" (for example deficit: (0,2,-)). The state is not changed.

STATE
Output the following table. For each type, the width of that type is the number of digits in the decimal representation of that type's value of Total. The "table form" of a resource vector is the string obtained by right-aligning each value to its type's width (padding on the left with spaces) and joining the values with single spaces. The "name row" is the string obtained by right-aligning the name of each type (A, B, ...) in the same way and joining them. Let L be the length of the name row; the widths of the four columns Allocation, Max, Need and Request are, respectively, the larger of 10 and L, the larger of 3 and L, the larger of 4 and L, and the larger of 7 and L.
Each row of the table is the string consisting of a heading (left-aligned and padded on the right with spaces to 9 characters) followed, for each of the four columns, by two spaces and that column's content (left-aligned and padded on the right with spaces to the column width), with all trailing whitespace removed. The content of a column for which no content is given is the empty string.
The first row has the heading "Process", and the column contents are, in order, "Allocation", "Max", "Need", "Request".
The second row has the empty string as its heading, and all four column contents are the name row.
Then, for each existing process in increasing order of process number, there is one row whose heading is the name of that process and whose column contents are, in order, the table forms of Allocation, Max, Need and Request. Here Request is the process's request vector in the wait queue if the process is blocked, and the zero vector otherwise.
The next row has the heading "Available", and the content of the Allocation column is the table form of Available (the other columns have no content).
The next row has the heading "Total", and the content of the Allocation column is the table form of Total.
The last row is "blocked queue: empty" if the wait queue is empty; otherwise it is "blocked queue: " followed by the requests in the wait queue, from the head, each written in the form "Pi R since t=S" (Pi is the process, R is the request vector, S is the command number at which it started waiting), joined with ", " (a comma and one space).

STATS
First, for each type in type order, output one line "X: allocated U/T (P%), requested Q". X is the name of the type, T is that type's value of Total, U is T minus that type's value of Available, and P is U multiplied by 100 and divided by T, with the second and later decimal places truncated, written as the integer part, ".", and exactly one digit for the first decimal place (for example 71.4, 100.0, 0.0). Q is the sum of that type's values over all request vectors in the wait queue.
Next, output "events: granted a, blocked b, unblocked c, released d, finished e, aborted f, cancelled g". a to g are the numbers of events of the respective kinds in the history.
Finally, if the history contains one or more events of kind unblocked, output "waits: n unblocked, total S, average A". n is their number, S is the sum of their waiting times, and A is S divided by n, with the third and later decimal places truncated, written as the integer part, ".", and exactly two digits for the first and second decimal places (for example 8.33, 10.00). If there are no events of kind unblocked, output "waits: none".

DETECT
Run the detection algorithm, and output "deadlocked: L" (L is the list of those processes) if there are deadlocked processes, or "no deadlock" if there are none.

VICTIMS
Finds a smallest set of processes that should be aborted to eliminate the deadlock. The state is not changed. First run the detection algorithm; if there are no deadlocked processes, output "no deadlock". Otherwise, order the nonempty sets S of deadlocked processes by the priority (1) fewer processes in S first, (2) smaller total of the sums of the Allocation of the processes in S first, (3) lexicographic order of the list of the process numbers of S sorted in increasing order, examine them in that order, and find the first S that satisfies the following condition. The condition is that running the detection algorithm in the state with all processes of S deleted (the Allocation of each process of S added to Available, the requests of the processes of S removed from the wait queue, and the processes of S removed) yields no deadlocked processes (the S consisting of all deadlocked processes always satisfies this condition). For the found S, output "victims: L" (L is the list of the processes of S).

RECOVER
Repeat the following. Run the detection algorithm; if there are no deadlocked processes, end the repetition. Otherwise, choose one of them according to the recovery policy, and apply to that process the same processing as ABORT (removing its request, returning its Allocation and deleting it, outputting "aborted Pi released U", recording in the history, and retrying). The choice according to the recovery policy is as follows.
ALLOC: the process with the smallest sum of Allocation. If there are several, the one among them with the largest process number.
NEED: the process with the largest sum of Need. If there are several, the one among them with the largest process number.
YOUNGEST: the process with the largest creation number.
After ending the repetition, output "recovered: n aborted" if the number n of aborted processes is 1 or more, or "no deadlock" if it is 0.

RECOVER ALL
Run the detection algorithm once; if there are no deadlocked processes, output "no deadlock". Otherwise, abort all of those processes in increasing order of process number. Each process receives the same processing as ABORT, except that no retry is performed in the middle. After all of them have been aborted, perform one retry and output "recovered: n aborted" (n is the number of aborted processes). The recovery policy is not used.

WAITGRAPH
Output the directed graph representing waiting relationships between processes (the wait-for graph). For each blocked process Pi, the types for which the value of its request vector is greater than the value of Available are the types that Pi is short of. When a process Pj other than Pi has one or more units of any of the types that Pi is short of in its Allocation, there is an edge from Pi to Pj, and the label of that edge is the types that Pi is short of for which the value of Pj's Allocation is positive. Output the edges in increasing order of i, and for the same i in increasing order of j, one per line in the form "Pi -> Pj on X" (X is the names of the label's types in type order separated by ",", for example A,C). If there are no edges at all, output "no wait edges". Note that a request waiting for the reason unsafe state may have no types it is short of; in that case there are no edges from that process.
Then output all cycles of this graph. A cycle is two or more mutually distinct processes Pa, Pb, ..., Pz such that the edges from Pa to Pb, from Pb to the next process, ..., and from Pz to Pa all exist. Each cycle is output exactly once in the form "cycle: Pa -> Pb -> ... -> Pz -> Pa", where Pa is the process with the smallest number among the processes it contains. Cycles are ordered by comparing the lists of processes written in this form (including the final Pa) from the beginning; at the first differing position, the one with the smaller process number comes first. If there are no cycles, output "no cycles".

GRAPH
Output the resource allocation graph for the case where each type has a single instance. If any value of Total is not 1, it is an error ("not single-instance"). Otherwise, consider the following three kinds of edges. If there is a process Pj that has type X in its Allocation, there is an assignment edge X -> Pj. For each blocked process Pi and each type X for which the value of its request vector is positive, there is a request edge Pi -> X. For each process Pi and each type X for which the value of Need is positive and the value of Pi's request vector in the wait queue (the zero vector if Pi is not blocked) is 0, there is a claim edge Pi -> X.
First output the assignment edges in type order, one per line, in the form "assign X -> Pj", then the request edges in increasing order of i, and for the same i in type order, in the form "request Pi -> X", and then the claim edges in the same order in the form "claim Pi -> X".
Then output all cycles that alternately follow only request edges and assignment edges. A cycle is a path such as Pa -> X -> Pb -> Y -> ... -> Pz -> Z -> Pa that repeatedly goes from a process to a type by a request edge and from that type to a process by an assignment edge and returns to the starting process, and in which the processes along the way are mutually distinct. Each cycle is output exactly once in the form "cycle: Pa -> X -> Pb -> Y -> ... -> Pz -> Z -> Pa", where Pa is the process with the smallest number among the processes it contains. Cycles are ordered by comparing the sequences of elements written in this form (including the final Pa) from the beginning; at the first differing position, the one with the smaller element comes first. Elements at the same position are either both processes or both types; processes are compared by process number, and types in the order A, B, C, .... If there are no cycles, output "no cycles". Claim edges are not used in cycles.

HISTORY, HISTORY id, HISTORY kind
Output the events of the history from oldest to newest, one line per event, in the form "t=S KIND Pi V". S is the command number of the event, KIND is the kind of the event, Pi is the process of the event, and V is the resource vector of the event. Only for events of kind unblocked, append " waited W" (W is the waiting time) after that. When id is given as the argument, output only the events whose process number is id (the process may already have been deleted). When kind is given as the argument, output only the events whose kind is kind. If there are no events to output, output "no events".

SNAPSHOT name
Save copies of the current Total, Available, all existing processes (process number, Max, Allocation, creation number), the wait queue and the history under the name name, and output "saved name". If a snapshot with the same name already exists, overwrite it. The four settings, the command number and the other snapshots are not saved.

RESTORE name
If there is no snapshot named name, it is an error ("unknown snapshot name"; for example "error: unknown snapshot s1"). Otherwise, replace Total, Available, the existing processes, the wait queue and the history with the contents at the time of saving (the number of resource types also becomes the one at the time of saving), and output "restored name". The snapshot is not deleted and remains, and it can be restored any number of times. The four settings do not change, and no retry is performed.

[Output format]
The output of each command consists of the lines defined in [Processing], output in command order. When a command outputs several lines, they are output in the order of the processing described in [Processing], and trace lines are output at the moment the check is performed.
The name of the process with number i is "Pi" (for example P3, P12).
A resource vector is written as its values in type order, separated by ",", and enclosed as a whole in "(" and ")" (for example (1,0,2)). No spaces are inserted.
A list of processes is the names of the processes separated by single spaces. A list whose order is not otherwise specified is in increasing order of process number.
All numbers are decimal integers (except P and A of STATS) with no extra leading zeros.
All output consists of ASCII characters, and every line ends with a newline (LF). Lines have no trailing whitespace, and no empty lines are output. The only line that begins with whitespace is the second row of the STATE table.
Whitespace within a string is a single space unless otherwise specified.

[Constraints]
- 1 <= N <= 1000
- The number m of integers given to RESOURCES is between 1 and 8 inclusive, and each value is between 1 and 99 inclusive.
- The number of integers in a resource vector v is between 0 and 9 inclusive, and each value is between 0 and 99 inclusive.
- ADD never makes a value of Total exceed 99.
- id is an integer between 0 and 99 inclusive. At most 12 processes exist at the same time, and at most 8 processes exist when SEQUENCES is executed.
- k of SEQUENCES is an integer between 0 and 50 inclusive.
- name is between 1 and 10 characters long inclusive.
- Every value that appears during computation is an integer whose absolute value is less than 2^31.
