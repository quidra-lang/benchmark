[Overview]
Write a program that handles Standard MIDI Files (SMF below). It reads the bytes of an SMF given as a hex dump and parses them, and it lists the events, re-encodes a song into an SMF (printing a hex dump), computes playback times and bar positions, pairs note-ons with note-offs, edits songs (transposition, quantization and so on), merges and splits tracks, prints statistics and displays a simple piano roll. Songs are given names and several of them can be held at the same time; editing commands rewrite a held song, and the result is reflected in later commands. Besides a hex dump, a song can also be given in the same text form that the DECODE command prints.

[Input format]
Input is read from standard input. The first line is the number of commands N. N commands follow, one per line. Immediately after the line of a HEX or TEXT command come the k data lines that the command reads (data lines are not counted in N).
Every line consists of words separated by single spaces, with no whitespace at the start or end of the line (however, consecutive spaces may appear inside a text-kind field of a TEXT event line). name and dest are song names: strings of 1 to 16 characters consisting of lowercase English letters, digits and _. Numeric arguments are decimal integers.
The command formats are as follows.
HEX name k
TEXT name k
DECODE name
ENCODE name
TIMING name
NOTES name
STATS name
ROLL name from to step
TRANSPOSE name n
TRANSPOSE name n channel
QUANTIZE name grid strength
VELOCITY name percent offset
TEMPO name num den
FILTER name c1 c2 ... (one or more channels are listed)
MERGE name
SPLIT name
COPY name dest
LIST
RUNNING word (word is ON or OFF)
NOTEOFF word (word is ZERO or KEEP)
A HEX data line consists of one or more byte values, each written as two uppercase hexadecimal digits, separated by single spaces. The bytes of the k lines concatenated in this order form the SMF byte sequence (the line breaks have no meaning).
Of the TEXT data lines, the first line is a header line and the second and later lines are event lines; both are written in the same form that DECODE prints (described below).

[Processing]
1. Song representation and terms
A song consists of a format (one of 0, 1, 2), a division (the number of ticks per quarter note) and a sequence of tracks. Tracks are numbered 0, 1, 2, ... from the first. Each track is a sequence of events, and each event has an absolute tick (the cumulative sum of the delta times) counted from the start of its track. In every track, the last event is END_OF_TRACK, and it is the only END_OF_TRACK in the track.
- Number of events: the total number of events in all tracks, including END_OF_TRACK.
- Song length: the maximum of the ticks of the END_OF_TRACK events of all tracks.
- Global order: the order of the events of all tracks arranged by ascending tick, by ascending track number when ticks are equal, and further by their order within the track for events of the same track.
- Channel messages: the seven event types NOTE_OFF, NOTE_ON, POLY_PRESSURE, CONTROL, PROGRAM, CHANNEL_PRESSURE and PITCH_BEND.
- Note-on: a NOTE_ON whose velocity is 1 or more. Note-off: a NOTE_OFF, or a NOTE_ON whose velocity is 0.
- x div y (x and y integers, y positive) denotes the largest integer not exceeding x/y (for negative numbers, rounding toward -infinity), and x mod y denotes x - y*(x div y).

2. Text representation of events
An event is represented by one line "tick track TYPE field1 field2 ...". tick is the absolute tick, track is the track number, TYPE is the type name shown below, and words are separated by single spaces. For a type without fields, the line ends with TYPE. Below, ch is a channel; in text it is written as 1 to 16, and in bytes it is represented as the value ch-1 in the low 4 bits of the status byte. In this document, hexadecimal values are written with the prefix 0x.

Channel messages (the type is determined by the high 4 bits of the status byte; ? stands for the low 4 bits holding the channel):
- NOTE_OFF ch note velocity: the bytes are 0x8? note velocity.
- NOTE_ON ch note velocity: the bytes are 0x9? note velocity.
- POLY_PRESSURE ch note pressure: the bytes are 0xA? note pressure.
- CONTROL ch controller value: the bytes are 0xB? controller value.
- PROGRAM ch program: the bytes are 0xC? program.
- CHANNEL_PRESSURE ch pressure: the bytes are 0xD? pressure.
- PITCH_BEND ch value: the bytes are 0xE? lsb msb, and value = lsb + 128*msb - 8192 (from -8192 to 8191).
Every data byte following a status byte is 0 to 127. In text, note is written as a note name, and every other value is written in decimal.

Note names: the note name of note number p (0 to 127) is one of C, C#, D, D#, E, F, F#, G, G#, A, A#, B, which correspond in this order to the values 0 to 11 of p mod 12, followed by the octave number p div 12 - 1 in decimal. For example, 60 is C4, 61 is C#4, 0 is C-1 and 127 is G9. Only sharps are used; flats are never used.

Exclusive events:
- SYSEX len data: the bytes are 0xF0, the length len (a variable-length quantity), and then len data bytes, in this order.
- SYSEX_ESCAPE len data: the bytes are 0xF7, the length len (a variable-length quantity), and then len data bytes, in this order.
data is the string of exactly 2*len characters obtained by writing each data byte as two uppercase hexadecimal digits and concatenating them without separators. When len is 0, the data field is not written and the line ends with len.

Meta events (the bytes are 0xFF, one byte holding the type number type, the length len (a variable-length quantity), and then len data bytes, in this order):
- type 0x00: SEQUENCE_NUMBER number. len is 2, and the data is the high byte and then the low byte of number (0 to 65535).
- type 0x01 to 0x07: in order, TEXT_EVENT, COPYRIGHT, TRACK_NAME, INSTRUMENT_NAME, LYRIC, MARKER, CUE_POINT (called the text kinds below). There is one field: the string obtained by regarding each data byte as an ASCII character, enclosed in double quotes ". len is unrestricted, and when it is 0 the field is "".
- type 0x20: CHANNEL_PREFIX ch. len is 1, and the data is ch-1.
- type 0x2F: END_OF_TRACK. len is 0, and there are no fields.
- type 0x51: TEMPO usec. len is 3; the number of microseconds per quarter note usec (1 to 16777215) is represented as 3 bytes, big-endian.
- type 0x54: SMPTE_OFFSET hr mn se fr ff. len is 5; the values of the 5 bytes (each 0 to 255) are written in decimal in this order.
- type 0x58: TIME_SIGNATURE nn/dd cc bb. len is 4, and the data is nn, e, cc, bb in this order. The denominator dd of the time signature is 2 to the power e, and in text "numerator/denominator" is written as one word (example: 3/4). nn is 1 to 255, e is 0 to 6, and cc and bb are 0 to 255.
- type 0x59: KEY_SIGNATURE key mode. len is 2, and the data is sf, mi in this order. sf is a signed byte in two's complement (-7 to 7), and mi is 0 (major) or 1 (minor). In text, the key name is written as two words.
- type 0x7F: SEQUENCER_SPECIFIC len data. len and data are written in the same way as for SYSEX.
- Any other type (including 0x08 to 0x1F, 0x80 to 0xFF and so on): META tt len data. tt is type written as two uppercase hexadecimal digits, and len and data are written in the same way as for SYSEX.

Key names: for sf = -7, -6, ..., 7, if mi is 0 the name is, in order, Cb, Gb, Db, Ab, Eb, Bb, F, C, G, D, A, E, B, F#, C# followed by a space and major, and if mi is 1 it is, in order, Ab, Eb, Bb, F, C, G, D, A, E, B, F#, C#, G#, D#, A# followed by a space and minor. For example, sf = -3, mi = 0 is Eb major, and sf = 4, mi = 1 is C# minor.

The header line is "HEADER f t d", where f is the format, t is the number of tracks and d is the division.

3. HEX: parsing an SMF
The byte sequence obtained from the k data lines is parsed as an SMF by the following procedure. Positions are byte offsets, with the first byte of the sequence at 0. When an error is found, parsing stops at that point, and the reason is reported together with the position shown after it in parentheses below. In that case the song is not registered, and if a song with the same name already exists, that song is not changed. If there is no error, the parsed song is registered as the song name (replacing any song with the same name).

Variable-length quantity: at most 4 bytes. It represents the value formed by placing the low 7 bits of each byte, from the first byte onward, from the most significant end, and it ends with a byte whose most significant bit is 0. A redundant representation padded at the front with 0x80 bytes is also valid. If the most significant bit of the 4th byte is also 1: variable-length value too long (the position of the first byte of that variable-length quantity).

Reading a chunk (a chunk whose ID is X is read starting at position p):
(1) If the number of remaining bytes (total length - p) is less than 8: truncated chunk (p).
(2) If the 4 bytes from p are not the ASCII codes of the 4 characters of X: bad chunk id (p).
(3) Let L be the value of the 4 bytes from p+4 read as big-endian. If p+8+L exceeds the total length: truncated chunk (p).
(4) The L bytes from p+8 are the chunk data, and the next chunk starts at p+8+L.

Header: read a chunk whose ID is MThd from position 0, and check the following in this order.
(1) If L is not 6: bad header length (4).
(2) Let format be the 2 bytes from position 8 (big-endian; the same applies below); if it is greater than 2: bad format (8).
(3) Let the number of tracks be the 2 bytes from position 10; if it is 0, or if format is 0 and the number of tracks is not 1: bad track count (10).
(4) Let division be the 2 bytes from position 12; if its most significant bit is 1: smpte timing not supported (12); if division is 0: bad division (12).

Tracks: starting at position 14, repeat the following as many times as the number of tracks.
(1) If 0 bytes remain: missing track (the total length).
(2) Read a chunk whose ID is MTrk, parse its data as an event sequence, and make it the next track.
If bytes remain after all tracks have been read: extra data (the position of the first remaining byte).

Parsing an event sequence: the chunk data is read from its start. Start with tick 0 and running status "none", and repeat the following while data remains. Below, "the data runs out" means that, when trying to read the next byte from the range of the chunk data, that byte is outside the range; in that case the error is truncated event (the start of that event, that is, the position of the start of its delta time).
(1) If the event read just before is END_OF_TRACK: event after end of track (the current position).
(2) Read the delta time as a variable-length quantity and add it to the tick.
(3) Look at the next byte b (if the data has run out, the error is truncated event). If b is less than 0x80: if the running status is "none", the error is data byte without running status (the position of b); otherwise b is not consumed and the value of the running status becomes the status. If b is 0x80 or more, b is consumed and becomes the status.
(4) If the status is 0x80 to 0xEF: it is a channel message. Set the running status to this status. Read data bytes one at a time: 1 byte if the high 4 bits of the status are 0xC or 0xD, and 2 bytes otherwise. If a byte read is 0x80 or more: bad data byte (the position of that byte).
(5) If the status is 0xF0 or 0xF7: set the running status to "none", read the length len as a variable-length quantity, and the following len bytes are the data.
(6) If the status is 0xFF: set the running status to "none", read the 1 byte of type and the length len (a variable-length quantity), and the following len bytes are the data.
In (5) and (6), if the len bytes of data do not fit within the range of the chunk data: truncated event (the position of the start of the event).
The meta event of (6) is checked in the following order after it has been read up to its data (both positions are the position of 0xFF). If type is one of 0x00, 0x20, 0x2F, 0x51, 0x54, 0x58, 0x59 and len differs from the length in the table above: bad meta length. If the usec of TEMPO is 0, the data of CHANNEL_PREFIX is greater than 15, the nn of TIME_SIGNATURE is 0 or its e is greater than 6, or the sf of KEY_SIGNATURE is outside -7 to 7 or its mi is greater than 1: bad meta data.
(7) If the status is 0xF1 to 0xF6 or 0xF8 to 0xFE: unknown status byte (the position of that status byte).
When all data has been read, if the track has no events or its last event is not END_OF_TRACK: missing end of track (the position just after the range of the chunk data).

4. TEXT: reading from text
A song is built from the k data lines, with the first line as the header line and the second and later lines as event lines. Line numbers are counted with the first data line as 1. When an error is found, reading stops at that point, and the line number and the reason are reported. The handling of the song in that case, and the registration when there is no error, are the same as for HEX.
The header line must consist of the 4 words "HEADER f t d", where f is 0 to 2, t is 1 to 65535 and d is 1 to 32767, and t must be 1 if f is 0. Otherwise: bad header (the line number is 1).
An event line consists of the 3 words tick, track and TYPE followed by fields. For a text-kind TYPE, everything after the single space immediately following TYPE is one field (the field may contain spaces). For any other TYPE, the fields are the words obtained by splitting the rest at spaces, and when the line ends with TYPE there are 0 fields. Each event line is checked in the following order.
(1) If TYPE is none of the type names in the table above: unknown event type.
(2) If the fields do not match the form of TYPE: bad value. Not matching means any of the following: the number of fields is different; a value is outside the range in the table above (channels 1 to 16, data bytes 0 to 127, the value of PITCH_BEND -8192 to 8191, and so on); a note name is none of the 128 names produced by the rule above; the denominator of TIME_SIGNATURE is none of 1, 2, 4, 8, 16, 32, 64; the two words of KEY_SIGNATURE are none of the key names; len is outside 0 to 1000000; data contains a character other than 0 to 9 and A to F, or its length is not 2*len; there is a data field although len is 0; the tt of META is not two characters consisting of 0 to 9 and A to F, or it denotes one of the types 0x00 to 0x07, 0x20, 0x2F, 0x51, 0x54, 0x58, 0x59, 0x7F; a text-kind field is not a string of 2 or more characters that starts with " and ends with ", or it contains " inside, excluding the two ends. The text-kind string is the part without the " at both ends.
(3) If track is greater than or equal to the number of tracks t of the header line: bad track.
(4) Let c be the number of the track currently being built (initially 0), and let E be whether track c already has an END_OF_TRACK. If track is less than c: out of order. If track is greater than c, and E is false or track is greater than c+1: missing end of track. If track is c and E is true: event after end of track. If track is c+1 and E is true, increase c by 1 and start a new track (the tick of the first event of the new track is unrestricted). If track is c, track c has events, and tick is less than the tick of its last event: out of order.
(5) If there is no error, append the event to the end of track c.
When all lines have been read, if c + 1 is less than t or track c has no END_OF_TRACK: missing end of track (the line number is k+1). When track c has no events at all, it is also regarded as having no END_OF_TRACK.

5. DECODE name
Print the header line, then, for the tracks from track 0 in order, print the events of each track in their order as event lines. The lines printed here can be read as TEXT data lines as they are.

6. ENCODE name
Encode the song into an SMF byte sequence and print it as a hex dump.
- The byte sequence is the header chunk followed by the track chunks of the tracks, from track 0 in order.
- The header chunk is 14 bytes: the 4 bytes of MThd, 4 bytes representing the length 6 (00 00 00 06), and then format, the number of tracks and division, each as 2 bytes big-endian.
- A track chunk is the 4 bytes of MTrk, 4 bytes big-endian representing the number of data bytes, and then the data. The data is, for each event of the track, the delta time (the tick of that event minus the tick of the previous event in the same track; for the first event, the tick itself) written as a variable-length quantity, followed by the byte representation of the event.
- Variable-length quantities are written in the shortest representation: split the value into groups of 7 bits from the low end, write them in order from the most significant nonzero group (a single byte 0x00 if the value is 0), and set the most significant bit to 1 in every group except the last. The len of SYSEX, SYSEX_ESCAPE and meta events is written in the same way.
- Running status: with RUNNING ON, the status byte of a channel message is omitted if it equals the status byte of the channel message written (or omitted) just before in the same track and no SYSEX, SYSEX_ESCAPE or meta event lies between them. At the start of a track there is nothing to compare with. With RUNNING OFF, the status byte is always written.
- With NOTEOFF ZERO, NOTE_OFF ch note velocity is written as the same bytes as NOTE_ON ch note 0 (0x9? note 0x00). The running status comparison also uses the rewritten status byte. With NOTEOFF KEEP, nothing is rewritten.
- The data of a text kind is the ASCII codes of the string, TEMPO is 3 bytes, SEQUENCE_NUMBER is 2 bytes big-endian, and the sf of KEY_SIGNATURE is the value plus 256 if it is negative. Everything else is as in the table of section 2.
The RUNNING and NOTEOFF settings affect only ENCODE, and the initial state is RUNNING ON, NOTEOFF KEEP.

7. TIMING name
For a song of format 2 this is an error. Convert the tick T of each event into a time (in milliseconds) by the tempo map and into a bar position by the time signatures.
Time: start with S = 0, last = 0, v = 500000; go through the TEMPO events in global order, and for each one whose tick is less than or equal to T, add (tick - last)*v to S, set last to tick, and set v to its usec. Finally, add (T - last)*v to S. Let m = S div division (the time truncated to microseconds), and write the time as the decimal representation of m div 1000, then ".", then the decimal representation of m mod 1000 padded with zeros to 3 digits (example: m = 1041666 gives 1041.666). If there are several TEMPO events at the same tick, the last one in global order takes effect from that tick on.
Bar position: start with st = 0, bar = 1, nn = 4, beat = division (the number of ticks in one bar is nn*beat). Go through the TIME_SIGNATURE events in global order, and for each one whose tick u is less than or equal to T, add (u - st + nn*beat - 1) div (nn*beat) (the value of (u - st)/(nn*beat) rounded up) to bar, set st to u, set nn to its numerator, and set beat to division*4 div denominator. Finally, with x = T - st, let bar number = bar + x div (nn*beat), beat number = (x mod (nn*beat)) div beat + 1, and tick number = x mod beat, and write "bar number:beat number:tick number" (example: 3:2:48). When the time signature changes in the middle of a bar, a new bar starts at that point.

8. NOTES name
Go through the events in global order and pair note-ons with note-offs. For each (channel, note number) pair, keep a queue of note-ons waiting for a partner. A note-on is appended to the end of the queue of its pair. For a note-off, if the queue of its pair is not empty, the note-off is paired with the note-on at the head of the queue (the one added earliest), that note-on is removed from the queue, and the two form one note. If the queue is empty, the note-off is unmatched. Note-ons left in the queues after all events have been processed are also unmatched.
A note has a start tick (the tick of the note-on), a length (the tick of the note-off minus the start tick), a channel, a note number and a velocity (the velocity of the note-on). Notes are sorted by ascending start tick, then by ascending channel when equal, then by ascending note number, and then by the global order of the note-on. Unmatched events are sorted in global order. This pairing is also used by QUANTIZE, STATS and ROLL.

9. Editing commands
TRANSPOSE, QUANTIZE, VELOCITY, TEMPO, FILTER, MERGE and SPLIT rewrite the song. When an error is reported, the song is not changed.
- TRANSPOSE name n [channel]: n is -127 to 127, and channel is 1 to 16. Add n to the note number of the NOTE_ON, NOTE_OFF and POLY_PRESSURE events: those of that channel when channel is given, and all of them when it is not. Events whose result is outside 0 to 127 are deleted.
- QUANTIZE name grid strength: grid is 1 to 1000000, and strength is 0 to 100. Pair the events in the same way as NOTES; the targets are the matched notes (note-on and note-off pairs) and the unmatched note-ons (on their own). With t the start tick of a target, let lower = (t div grid)*grid and upper = lower + grid; if t - lower is less than or equal to upper - t then g = lower, otherwise g = upper (exactly halfway gives the earlier one, lower). The shift delta is (g - t)*strength/100 rounded to an integer, where an exact .5 is rounded toward the larger value (toward +infinity). That is, delta = (2*(g - t)*strength + 100) div 200. Add delta to both the tick of the note-on and the tick of the matched note-off. Then, in each track, sort the events other than END_OF_TRACK by ascending tick (events with the same tick keep their order from before the sort), place END_OF_TRACK after them, and set the tick of END_OF_TRACK to the larger of "its original tick" and "the maximum tick of the other events".
- VELOCITY name percent offset: percent is 0 to 1000, and offset is -127 to 127. Change the velocity v of each note-on to (v*percent + 50) div 100 + offset, and make it 1 if it is less than 1 and 127 if it is greater than 127 (this limiting is called "clamping"). Note-offs are not changed.
- TEMPO name num den: num and den are 1 to 1000. Change the usec of each TEMPO to (2*usec*den + num) div (2*num) (the value of usec*den/num rounded half up). If no track has a TEMPO at tick 0, insert a TEMPO whose value is usec = 500000 converted in the same way, at tick 0 at the beginning of track 0. If any of the converted values (including the inserted value) is outside 1 to 16777215, it is the error tempo out of range.
- FILTER name c1 c2 ...: each channel is 1 to 16 (duplicates are allowed). Delete the channel messages whose channel is none of c1, c2, .... All other events are kept.
- MERGE name: if format is not 1, it is the error not format 1. Make a single track consisting of all events other than END_OF_TRACK arranged in global order, followed by an END_OF_TRACK whose tick is the song length, and set format to 0.
- SPLIT name: if format is not 0, it is the error not format 0. Distribute the events of the original track except END_OF_TRACK, keeping their original order: events that are not channel messages go to track 0, and channel messages go to a track for each channel. The per-channel tracks are numbered track 1, 2, ... in ascending order of the channels that occur. At the end of each track, place an END_OF_TRACK with the same tick as the original END_OF_TRACK, and set format to 1.

10. STATS name
For a song of format 2 this is an error. Print statistics about the notes given by the NOTES pairing. The polyphony at an integer tick x is the number of notes satisfying "start tick <= x < start tick + length" (notes of length 0 are not counted); find its maximum and the smallest x at which the maximum is reached.

11. ROLL name from to step
from must be 0 to 10000000, to must be 1 to 10000000, step must be 1 to 10000000, to must be greater than from, and the number of columns (to - from + step - 1) div step must be 64 or less. Column i (i = 0, 1, ...) represents the range of ticks from a = from + i*step up to but not including a + step. Using the notes given by the NOTES pairing, for each pair of a note number p and a column, the character is # if some note with note number p satisfies "a <= start tick < a + step"; otherwise = if some note with note number p satisfies "start tick <= a < start tick + length"; and . if neither (channels are not distinguished). Only the note numbers that contain at least one character other than . are printed, one line each, in descending order of note number.

12. COPY, LIST, RUNNING, NOTEOFF
- COPY name dest: register a copy of the song name under the name dest (replacing any song with the same name). From then on, the two songs change independently.
- LIST: print all registered songs in ASCII order of their song names (lexicographic order).
- RUNNING word, NOTEOFF word: change the settings of ENCODE. If word is neither of the two given in the command format, it is the error bad argument.

13. Order of error checks
Commands other than HEX and TEXT are checked in the following order, and the first error that applies is reported.
(1) The command name is not in the command formats: unknown command.
(2) No song with the song name name (for COPY, the first song name) is registered: no song <song name> (the song name that was given).
(3) A numeric argument is out of range, the range conditions of ROLL are not satisfied, or the word of RUNNING or NOTEOFF is not valid: bad argument.
(4) Errors specific to each command (the format conditions, tempo out of range).
The error for the format condition of TIMING and STATS is format 2 not supported. HEX and TEXT skip all k data lines, whether or not there is an error, before proceeding to the next command.

[Output format]
For each command, print the following lines in this order. Words within a line are separated by single spaces (the contents of text-kind strings are printed as they are), no line has trailing whitespace, and every line ends with a newline. Numbers are written in decimal without extra leading zeros (negative numbers with -), and unless specified otherwise, nothing else is printed. Below, the parts enclosed in < > are replaced by values. The period at the end of each item is sentence punctuation and is not included in the output.
- Error: print only the single line error: <reason>. A HEX parsing error is error: byte <position>: <reason>, a TEXT reading error is error: line <line number>: <reason>, and when a song is not registered it is error: no song <song name>.
- HEX, TEXT: on success, loaded <song name> format <format> tracks <number of tracks> division <division> events <number of events>.
- DECODE: the header line and each event line.
- ENCODE: one line for every 16 bytes of the byte sequence, <position>: <byte> <byte> .... The position is the position of the first byte of that line written as 4 uppercase hexadecimal digits (zero-padded), and each byte is 2 uppercase hexadecimal digits. The last line may have fewer than 16 bytes. After that, <total number of bytes> bytes.
- TIMING: for each event in global order, <tick> <track> <TYPE> <time> <bar number:beat number:tick number>. After that, for the song length T, end <T> <time> <bar number:beat number:tick number>.
- NOTES: notes <number of notes> unmatched <number of unmatched events>. Then, for each note, <start tick> <length> <channel> <note name> <velocity>. Then, for each unmatched event, unmatched <on or off> <tick> <track> <channel> <note name> (on for a note-on, off for a note-off).
- TRANSPOSE: transposed <number of events that had n added to their note number and were kept> dropped <number of deleted events>. Then, for each deleted event, in ascending order of track number and in order within the track, dropped <tick> <track> <TYPE> <channel> <original note name>.
- QUANTIZE: quantized <number of targets> moved <number of targets whose delta was not 0>.
- VELOCITY: velocity <number of converted note-ons> clamped <number of clamped note-ons>.
- TEMPO: scaled <number of converted existing TEMPO events>. If a TEMPO was inserted, the next line is inserted 0 0 TEMPO <usec> (inserted and a space, followed by the event line of the inserted TEMPO).
- FILTER: removed <number of deleted events>.
- MERGE: merged <original number of tracks> tracks events <number of events after merging>.
- SPLIT: split tracks <number of tracks after splitting> events <number of events after splitting>.
- STATS: print the lines (1) to (6) below in this order.
(1) format <format> tracks <number of tracks> division <division> events <number of events>.
(2) notes <number of notes> unmatched <number of unmatched events>.
(3) For each channel that has one or more notes, one line each in ascending order of channel: channel <channel> notes <number of notes of that channel> range <note name of the lowest note of that channel> <note name of the highest note>.
(4) range <note name of the lowest note of all notes> <note name of the highest note>. If there are no notes, range none.
(5) length <song length> ticks <time of the song length> ms. The time is written in the same way as in TIMING.
(6) polyphony <maximum polyphony> at <smallest tick at which the maximum is reached>. If the maximum is 0, polyphony 0.
- ROLL: each line is the note name padded on the right with spaces to 4 characters, one space, and the characters of the columns (#, =, .) in column order. If there are no lines to print, empty.
- COPY: copied <name> to <dest>.
- LIST: for each song, <song name> format <format> tracks <number of tracks> division <division> events <number of events>. If there are no songs, no songs.
- RUNNING: running on or running off. NOTEOFF: noteoff zero or noteoff keep.

[Constraints]
- 1 <= N <= 300, the whole input has at most 2000 lines, and each line has at most 1000 characters. The k of HEX and TEXT is at least 1 and at most 300.
- Each command has the number of arguments given in its format, and numeric arguments are valid decimal integers (without extra leading zeros or +, and with - for negative numbers). Every decimal integer appearing in the input (including those in TEXT data lines) has an absolute value of at most 10^9.
- A HEX byte sequence is at most 4096 bytes. The data of text-kind meta events consists only of bytes in the range 0x20 to 0x7E other than 0x22 (").
- TEXT data lines consist only of printable ASCII characters. If the first word of the first line is HEADER and the line consists of 4 words, the remaining 3 words are decimal integers. Event lines have 3 or more words, and tick and track are decimal integers of 0 or more. The fields that hold integers (the fields other than note names, data, tt, text-kind fields, the first field of TIME_SIGNATURE and the fields of KEY_SIGNATURE) contain valid decimal integers, and the first field of TIME_SIGNATURE has the form of two decimal integers joined by /. Values may be out of range.
- Every song has at most 17 tracks and at most 1000 events, and at every point in time all ticks are at most 10000000.
- For a song on which TIMING is executed, the denominator of every TIME_SIGNATURE divides division*4. The byte sequence of a song on which ENCODE is executed is shorter than 65536 bytes (positions fit in 4 hexadecimal digits).
- Intermediate values of the calculations may exceed 2^31, but their absolute values stay below 2^53. Compute with a type that represents integers in this range exactly, such as 64-bit integers. No floating-point approximation is needed.
