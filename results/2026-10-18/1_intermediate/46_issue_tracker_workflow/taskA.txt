[Overview]
Write a program that manages the issues of a software development team (an issue tracker). The program registers users and issues (bugs, tasks and stories) and, while advancing the date, processes state transitions that follow the workflow defined for each issue type, setting assignees and reviewers, estimates, comments, links between issues (blocks and duplicates), and the planning, start and end of sprints. It also searches issues with a query expression and displays issue details, history, the board, the workload, the list of sprints and burndowns. The program reads commands from standard input, processes them one at a time in the order written, and writes the results to standard output.

[Input format]
The first line contains the number N of command lines that follow. Each of the following N lines is one command. Each line consists of one or more tokens separated by single ASCII spaces, with no whitespace at the start or end of the line. The program ends after processing all N command lines.
In the descriptions below, <...> denotes a part where a value goes. The symbols < and > themselves never appear in the input or the output (however, a < or > appearing inside the query expression of QUERY is a comparison operator).

The commands are as follows.

Date and registration:
DAY <day>
USER <user>
CREATE <issue> <type> <priority> <title>

Editing issues:
PRIORITY <issue> <priority>
ASSIGN <issue> <userspec>
REVIEWER <issue> <userspec>
ESTIMATE <issue> <points>
COMMENT <issue> <user> <text>
MOVE <issue> <state>

Links:
LINK <issue1> <relation> <issue2>
UNLINK <issue1> <relation> <issue2>

Sprints:
SPRINT NEW <sprint>
SPRINT ADD <sprint> <issue>
SPRINT REMOVE <sprint> <issue>
SPRINT START <sprint>
SPRINT END <sprint>

Display:
QUERY <query>
SHOW <issue>
HISTORY <issue>
BOARD
WORKLOAD
SPRINTS
BURNDOWN <sprint>

The format and meaning of each value are as follows.
- <day>, <issue>, <issue1>, <issue2> and <points> are decimal integers without extra leading zeros.
- <user> (a user name) is a string of lowercase English letters. <userspec> is either a <user> or a single ASCII hyphen "-"; "-" means "none".
- <sprint> (a sprint name) is a string that starts with a lowercase English letter and consists of lowercase English letters and digits.
- <type>, <priority>, <state> and <relation> are strings consisting of uppercase English letters and "_".
- <title> is the string obtained by joining the 5th and later tokens of the CREATE line (counting the command name as the 1st token), in this order, with a single ASCII space between consecutive tokens (that is, from the 5th token of the line to the end of the line). Likewise, <text> is the 4th and later tokens of the COMMENT line, and <query> is the 2nd and later tokens of the QUERY line, each joined with a single ASCII space between consecutive tokens.

[Processing]
## 1. Initial state
At the start, the current day is 1, and there are no users, no issues and no sprints.

## 2. Issues
- An issue has an issue number, a type, a priority, a title, a state, an assignee, a reviewer, an estimate, a sprint (the sprint it belongs to), a comment count, a set of blocked issues, a set of blockers, a duplicate target, a set of duplicate sources, and a history (a sequence of lines). An issue is identified by its issue number.
- There are three types: BUG (bug), TASK (task) and STORY (story).
- There are four priorities: LOW, MEDIUM, HIGH and CRITICAL, increasing in this order (LOW is the lowest and CRITICAL is the highest priority).
- The assignee and the reviewer are each one user or "none"; the estimate is an integer or "none"; the sprint is one sprint or "none"; the duplicate target is one issue or "none".
- When an issue is created, its state is the initial state of its type (section 3); the assignee, reviewer, estimate, sprint and duplicate target are all "none"; the comment count is 0; and the set of blocked issues, the set of blockers, the set of duplicate sources and the history are empty.
- "Issue number order" means ascending order of issue numbers regarded as integers.
- The "points" of an issue are its estimate if the estimate is an integer, and 0 if it is "none".
- In the output, "none" is written as a single hyphen "-".

## 3. Workflows
The states and transitions of issues are as follows for each type. The first state in the state sequence is the initial state. "A->B" means that a transition from state A to state B is possible; transitions not listed here (including a transition to the same state) are not possible.
- BUG: the state sequence is OPEN, TRIAGED, IN_PROGRESS, REVIEW, RESOLVED, CLOSED, REOPENED. The transitions are the following 9: OPEN->TRIAGED, TRIAGED->IN_PROGRESS, IN_PROGRESS->REVIEW, REVIEW->IN_PROGRESS, REVIEW->RESOLVED, RESOLVED->CLOSED, RESOLVED->REOPENED, CLOSED->REOPENED, REOPENED->IN_PROGRESS.
- TASK: the state sequence is OPEN, IN_PROGRESS, DONE. The transitions are the following 3: OPEN->IN_PROGRESS, IN_PROGRESS->OPEN, IN_PROGRESS->DONE.
- STORY: the state sequence is BACKLOG, READY, IN_PROGRESS, REVIEW, DONE. The transitions are the following 6: BACKLOG->READY, READY->BACKLOG, READY->IN_PROGRESS, IN_PROGRESS->REVIEW, REVIEW->IN_PROGRESS, REVIEW->DONE.
An issue whose state is RESOLVED, CLOSED or DONE is called a "done" issue, and any other issue is called a "not done" issue.

## 4. Links
- The relation "issue a blocks issue b" (b cannot be done until a is done) is called a "blocking link" and is written "a->b". When a->b exists, b is in the set of blocked issues of a, and a is in the set of blockers of b.
- The blockers of issue y that are not done are called the "unfinished blockers" of y.
- Issue y is said to be "blocked" when y is not done and has one or more unfinished blockers.
- Block notification: for an operation that changes the state of an issue or a blocking link, for each affected issue y (specified in the description of each command), compare whether y is blocked immediately before and immediately after the operation. If y was not blocked and becomes blocked, output one line "BLOCKED <issue number of y>"; if y was blocked and is no longer blocked, output one line "UNBLOCKED <issue number of y>"; if nothing changed, output nothing. When there are several affected issues, examine them and output in issue number order.
- The relation "issue a is a duplicate of issue b" is called a "duplicate link". When a duplicate link is created, the duplicate target of a becomes b, and a is added to the set of duplicate sources of b. An issue whose duplicate target is not "none" is called a "duplicate issue".

## 5. Users
- A user is identified by the user name. "User name order" is the lexicographic order comparing user names by character code (when one is a prefix of the other, the shorter one comes first; example: the order is ann, anna, ben).
- The "WIP count" of user u is the number of issues whose assignee is u and whose state is IN_PROGRESS. The upper limit of the WIP count is 3.

## 6. Sprints
- A sprint has a sprint name, a phase, a start day, an end day, a velocity and a daily record, and is identified by its sprint name. The phase is one of PLANNED (planned), ACTIVE (in progress) and ENDED (ended), and is PLANNED when the sprint is created. At most one sprint can be ACTIVE at a time.
- The "members" of sprint s are the issues whose sprint is s.
- The "total points" of s are the sum of the points of all members, and the "remaining points" are the sum of the points of the members that are not done. If there are no members, both are 0.
- The "summary" of s is the string "issues <number of members> points <total points>".
- The daily record is a mapping from days to remaining points, and is empty when the sprint is created. Each time the processing of one command finishes (including a command that resulted in an error), if there is an ACTIVE sprint at that moment, the record of that sprint for the current day is set to the remaining points at that moment (if a record for the same day already exists, it is overwritten). In addition, SPRINT START and SPRINT END also write records (see their descriptions).

## 7. History
To the history of an issue, the history content specified in the description of each command is appended at the end as one line "day <d> <content>", prefixed with the current day d at that moment.

## 8. Error handling
For each command, check the error conditions given in its description in order of their numbers, and for the first one that applies, output only the single line "ERROR <message>". A command that results in an error outputs nothing else and does not change any state at all (it does not append to any history either). Where an error description says "check the issue", the error is ERROR unknown issue if no issue with the issue number specified by the command exists; "check the user" means ERROR unknown user if no user with the specified user name (excluding "-") exists; "check the sprint" means ERROR unknown sprint if no sprint with the specified sprint name exists.

## 9. Processing of each command

### DAY <day>
Errors:
1. <day> is smaller than the current day: ERROR day backwards
Set the current day to <day> and output "DAY <day>". <day> may be equal to the current day.

### USER <user>
Errors:
1. A user with the same user name already exists: ERROR user exists
Register the user and output "USER <user>".

### CREATE <issue> <type> <priority> <title>
Errors:
1. An issue with the same issue number already exists: ERROR issue exists
2. <type> is none of BUG, TASK and STORY: ERROR bad type
3. <priority> is none of LOW, MEDIUM, HIGH and CRITICAL: ERROR bad priority
Create the issue, append "CREATE <type> <priority>" to its history, and output "CREATE <issue> <type> <priority> <initial state>".

### PRIORITY <issue> <priority>
Errors:
1. Check the issue
2. <priority> is none of LOW, MEDIUM, HIGH and CRITICAL: ERROR bad priority
3. The issue is done: ERROR issue done
4. <priority> is the same as the current priority: ERROR no change
Let p be the priority before the change. Set the priority to <priority>, append "PRIORITY <p> <priority>" to the history, and output "PRIORITY <issue> <p> <priority>".

### ASSIGN <issue> <userspec>
Let u be the user denoted by <userspec> ("none" if it is "-").
Errors:
1. Check the issue
2. Check the user
3. The issue is done: ERROR issue done
4. u is the same as the current assignee (including the case where both are "none"): ERROR no change
5. u is "none" and the state of the issue is IN_PROGRESS or REVIEW: ERROR assignee required
6. The state of the issue is IN_PROGRESS and the WIP count of u is 3 or more: ERROR wip limit <userspec>
7. The state of the issue is REVIEW and u is the same as the current reviewer: ERROR reviewer is assignee
Set the assignee to u, append "ASSIGN <userspec>" to the history, and output "ASSIGN <issue> <userspec>".

### REVIEWER <issue> <userspec>
Let u be the user denoted by <userspec> ("none" if it is "-").
Errors:
1. Check the issue
2. Check the user
3. The issue is done: ERROR issue done
4. u is the same as the current reviewer (including the case where both are "none"): ERROR no change
5. u is "none" and the state of the issue is REVIEW: ERROR reviewer required
6. The state of the issue is REVIEW and u is the same as the current assignee: ERROR reviewer is assignee
Set the reviewer to u, append "REVIEWER <userspec>" to the history, and output "REVIEWER <issue> <userspec>".

### ESTIMATE <issue> <points>
Errors:
1. Check the issue
2. <points> is none of 0, 1, 2, 3, 5, 8, 13 and 21: ERROR bad estimate
3. The issue is done: ERROR issue done
4. <points> is the same as the current estimate: ERROR no change
Let e be the estimate before the change (- if it is "none"). Set the estimate to <points>, append "ESTIMATE <e> <points>" to the history, and output "ESTIMATE <issue> <e> <points>".

### COMMENT <issue> <user> <text>
Errors:
1. Check the issue
2. Check the user
Done issues can also be commented on. Increase the comment count by 1, append "COMMENT <user> <text>" to the history, and output "COMMENT <issue> <comment count after the increase>".

### MOVE <issue> <state>
Let f be the current state of the issue and t be <state>.
Errors:
1. Check the issue
2. The issue is a duplicate issue: ERROR duplicate of <issue number of the duplicate target>
3. t is not in the state sequence of the issue's type (section 3): ERROR bad state
4. f->t is not among the transitions of the issue's type (section 3): ERROR cannot move <f> to <t>
5. t is IN_PROGRESS and one of the following applies (checked from top to bottom):
  - The type of the issue is STORY, and either there is no ACTIVE sprint or the issue's sprint is not the ACTIVE sprint: ERROR not in active sprint
  - The assignee is "none": ERROR no assignee
  - The WIP count of the assignee is 3 or more: ERROR wip limit <user name of the assignee>
6. t is REVIEW and one of the following applies (checked from top to bottom):
  - The reviewer is "none": ERROR no reviewer
  - The reviewer is the same as the assignee: ERROR reviewer is assignee
7. t is DONE or RESOLVED and the issue has unfinished blockers: ERROR blocked by <issue number of the unfinished blocker with the smallest issue number>
8. t is READY and the estimate is "none": ERROR no estimate
If there is no error, change the issue to state t.

The procedure for changing issue x to state t is as follows (it is also used when creating a duplicate link). Let f be the state of x before the change. Output "MOVE <issue number of x> <f> <t>", append "MOVE <f> <t>" to the history of x, and set the state of x to t. Then perform block notification (section 4) with all issues in the set of blocked issues of x as the affected issues (x itself is not included in the affected issues, so no notification about x is output even if whether x is blocked changes).

### LINK <issue1> <relation> <issue2>
Let a be the issue <issue1> and b be the issue <issue2>.
Errors:
1. <relation> is neither BLOCKS nor DUPLICATES: ERROR bad link
2. Check the issue (both a and b)
3. a and b are the same issue: ERROR self link
If <relation> is BLOCKS, then check the following errors.
4. a->b already exists: ERROR link exists
5. Starting from b and following blocking links in their direction one or more times, a can be reached (that is, creating a->b would make a cycle): ERROR cycle
6. b is done: ERROR issue done
If there is no error, create a->b, append "LINK BLOCKS <issue number of b>" to the history of a and "LINK BLOCKED_BY <issue number of a>" to the history of b, and output "LINK <issue number of a> BLOCKS <issue number of b>". Then perform block notification with b as the affected issue.
If <relation> is DUPLICATES, then check the following errors.
4. a and b have different types: ERROR type mismatch
5. a is done: ERROR issue done
6. b is a duplicate issue: ERROR target is duplicate
If there is no error, create the duplicate link saying that a is a duplicate of b, append "LINK DUPLICATES <issue number of b>" to the history of a and "LINK DUPLICATED_BY <issue number of a>" to the history of b, and output "LINK <issue number of a> DUPLICATES <issue number of b>". Then change a to CLOSED if its type is BUG, or to DONE if its type is TASK or STORY (perform the change procedure described under MOVE; the transitions of section 3 and the error conditions of MOVE are not checked). Finally, if the sprint of a is not "none" and the phase of that sprint is not ENDED, set the sprint of a to "none" and append "SPRINT REMOVE <name of that sprint>" to the history of a (nothing is output for this).

### UNLINK <issue1> <relation> <issue2>
Let a be the issue <issue1> and b be the issue <issue2>.
Errors:
1. <relation> is not BLOCKS: ERROR bad link
2. Check the issue (both a and b)
3. a->b does not exist: ERROR no link
Remove a->b, append "UNLINK BLOCKS <issue number of b>" to the history of a and "UNLINK BLOCKED_BY <issue number of a>" to the history of b, and output "UNLINK <issue number of a> BLOCKS <issue number of b>". Then perform block notification with b as the affected issue.

### SPRINT NEW <sprint>
Errors:
1. A sprint with the same sprint name already exists: ERROR sprint exists
Create the sprint and output "SPRINT NEW <sprint>".

### SPRINT ADD <sprint> <issue>
Let s be that sprint.
Errors:
1. Check the sprint
2. Check the issue
3. The phase of s is ENDED: ERROR sprint ended
4. The issue is done: ERROR issue done
5. The sprint of the issue is not "none" and the phase of that sprint is not ENDED (including the case where it is s): ERROR in sprint <name of the issue's sprint>
6. The state of the issue is BACKLOG: ERROR not ready
Set the sprint of the issue to s (if the issue's sprint was an ENDED sprint, it is replaced), append "SPRINT ADD <name of s>" to the history of the issue, and output "SPRINT ADD <name of s> <issue> <summary of s>". The summary is the one after the addition.

### SPRINT REMOVE <sprint> <issue>
Let s be that sprint.
Errors:
1. Check the sprint
2. Check the issue
3. The phase of s is ENDED: ERROR sprint ended
4. The sprint of the issue is not s: ERROR not in sprint
5. The issue is done: ERROR issue done
Set the sprint of the issue to "none", append "SPRINT REMOVE <name of s>" to the history of the issue, and output "SPRINT REMOVE <name of s> <issue> <summary of s>". The summary is the one after the removal.

### SPRINT START <sprint>
Let s be that sprint.
Errors:
1. Check the sprint
2. The phase of s is not PLANNED: ERROR sprint not planned
3. Another sprint is ACTIVE: ERROR sprint active <name of that sprint>
4. s has no members: ERROR sprint empty
Set the phase of s to ACTIVE and its start day to the current day, set the record for the start day to the remaining points of s, and output "SPRINT START <name of s> day <start day> <summary of s> remaining <remaining points>". It is fine if some members are already done.

### SPRINT END <sprint>
Let s be that sprint.
Errors:
1. Check the sprint
2. The phase of s is not ACTIVE: ERROR sprint not active
First, set the record for the current day to the remaining points of s. Next, set the velocity of s to the sum of the points of the members of s that are done, set the phase of s to ENDED, and set its end day to the current day. Output "SPRINT END <name of s> day <end day> velocity <velocity> done <number of done members> returned <number of members that are not done>". Then, for the members that are not done, one at a time in issue number order, set the issue's sprint to "none" (return it to the backlog), append "SPRINT RETURN <name of s>" to the history of that issue, and output "RETURNED <issue>". The sprint of the done members stays s.

### QUERY <query>
Search issues with the query expression. The interpretation of the query expression is described in section 10. If the query expression has an error, output the error determined in section 10. Otherwise, take all issues for which the query expression is true, and order them by priority from highest to lowest, and within the same priority in issue number order. First output "QUERY <count>", then output one line per issue: "<issue> <type> <priority> <state> <assignee> <estimate> <title>". The assignee is a user name or -, and the estimate is an integer or -. Even when there are no issues at all, output "QUERY 0" if the query expression has no error.

### SHOW <issue>
Errors:
1. Check the issue
Output the following 5 lines in order. Here, a "number list" is the string obtained by joining issue numbers in issue number order with commas "," (no spaces), or - if there are no issues.
- "ISSUE <issue> <type> <priority> <state> blocked <b>", where b is yes if the issue is blocked and no otherwise.
- "TITLE <title>"
- "PEOPLE assignee <assignee> reviewer <reviewer>"
- "PLAN estimate <estimate> sprint <sprint> comments <comment count>"
- "LINKS blocks <number list of blocked issues> blocked_by <number list of blockers> duplicate_of <issue number of the duplicate target> duplicated_by <number list of duplicate sources>"
The assignee, reviewer, sprint and duplicate target are a user name, a user name, a sprint name and an issue number respectively, or -; the estimate is an integer or -. The blockers list includes all blockers (including done ones).

### HISTORY <issue>
Errors:
1. Check the issue
First output "HISTORY <issue> <number of history lines>", then output all history lines of that issue in the order they were appended.

### BOARD
There are no errors. First output "BOARD". Then output one line for each of the types BUG, TASK and STORY in this order: the type name followed, for each state in the order of that type's state sequence (section 3), by one ASCII space, the state name, one ASCII space, and the number of issues of that type in that state (example: TASK OPEN 2 IN_PROGRESS 1 DONE 0). Finally output "TOTAL <number of issues> open <number of issues not done> done <number of done issues>".

### WORKLOAD
There are no errors. First output "WORKLOAD <number of users>", then output all users in user name order, one per line, as "<user> assigned <a> in_progress <p> review <r> reviewing <v> points <t>". a is the number of issues that are not done and whose assignee is that user; p and r are the numbers of those issues whose state is IN_PROGRESS and REVIEW respectively; v is the number of issues whose reviewer is that user and whose state is REVIEW; t is the sum of the points of the issues counted in a.

### SPRINTS
There are no errors. First output "SPRINTS <number of sprints>", then output all sprints in creation order, one per line. The line format depends on the phase as follows.
- PLANNED: "<sprint> PLANNED <summary>"
- ACTIVE: "<sprint> ACTIVE start <start day> <summary> remaining <remaining points>"
- ENDED: "<sprint> ENDED start <start day> end <end day> velocity <velocity>"

### BURNDOWN <sprint>
Let s be that sprint.
Errors:
1. Check the sprint
2. The phase of s is PLANNED: ERROR sprint not started
Let the last day L be the current day if s is ACTIVE, or the end day if s is ENDED. First output "BURNDOWN <name of s> <phase> days <L - start day + 1>", then for each day d from the start day to L, in ascending order of days, output one line "day <d> <value>". <value> is the record, among the daily records of s, for the largest day that is <= d and has a record (the start day always has a record).

## 10. Query expressions
(1) Splitting into tokens
Examine the query expression one character at a time from the beginning and split it into tokens. An ASCII space separates tokens and is not part of any token. "(" and ")" each form a token of exactly one character. Any other characters form a token consisting of the longest run that is not interrupted by an ASCII space, "(" or ")" (example: "(priority>=HIGH OR id=3)" becomes the 5 tokens "(", "priority>=HIGH", "OR", "id=3", ")").
A token written exactly as AND, OR or NOT in uppercase English letters is an operator, "(" and ")" are parentheses, and every other token is a "condition".

(2) Grammar
The query expression follows the grammar below ({ ... } denotes zero or more repetitions, and | denotes "or").
  expr = term { OR term }
  term = factor { AND factor }
  factor = NOT factor | ( expr ) | condition
That is, NOT binds most tightly, then AND, and OR binds most loosely; the contents of parentheses are grouped first. NOT a is the negation of a; a AND b is true when both a and b are true; a OR b is true when at least one of a and b is true.

(3) Error detection
Read the tokens one at a time from the beginning, and check for errors with the following procedure. For the first error found, output its single error line, and do not examine any later tokens. The state is either "expecting an operand" or "expecting an operator"; initially it is expecting an operand, and the parenthesis depth is 0.
- If the token read while expecting an operand is NOT, the state stays expecting an operand. If it is "(", increase the parenthesis depth by 1 and stay expecting an operand. If it is a condition, perform the check of (4), and if there is no error, the state becomes expecting an operator. If it is AND, OR or ")", it is a syntax error.
- If the token read while expecting an operator is AND or OR, the state becomes expecting an operand. If it is ")": if the parenthesis depth is 0, it is a syntax error; otherwise decrease the depth by 1 and stay expecting an operator. If it is NOT, "(" or a condition, it is a syntax error.
- When all tokens have been read, if the state is expecting an operand or the parenthesis depth is not 0, it is a syntax error at the end.
For a syntax error when reading token t, output "ERROR syntax near <t>"; for a syntax error at the end, output "ERROR syntax at end". If this procedure finds no error, the query expression follows the grammar of (2).

(4) Checking a condition
Split the condition token c into F (the field name), which is the longest leading part consisting of lowercase English letters (a to z), the operator O immediately after it, and the remaining part V (the value). If the string immediately after F starts with one of ">=", "<=" and "!=", O is those 2 characters; otherwise, if it starts with one of "=", "<", ">" and "~", O is that 1 character. Check the following in order, and the first one that applies is the error.
1. F is empty, O is not found, or V is empty: ERROR syntax near <c>
2. F is none of the field names in the table below: ERROR unknown field <F>
3. O is not an operator usable with that field: ERROR bad operator <c>
4. V is not a value usable with that field: ERROR bad value <c>
Examples: "Type=BUG" and "priority>" match 1, "owner=bob" matches 2, "type<TASK" matches 3, and "status==DONE" (O is "=" and V is "=DONE") matches 4.

List of fields (field name: value of the issue. usable operators. usable values)
- id: the issue number. = != < <= > >=. A string of 1 to 6 characters consisting only of digits (0 to 9), representing its decimal value (leading zeros are allowed).
- type: the type. = !=. One of BUG, TASK and STORY.
- status: the state. = !=. Any state name that appears in section 3 (OPEN, TRIAGED, IN_PROGRESS, REVIEW, RESOLVED, CLOSED, REOPENED, DONE, BACKLOG, READY).
- priority: the priority. = != < <= > >=. One of LOW, MEDIUM, HIGH and CRITICAL. Order is compared by the levels of section 2.
- assignee: the assignee. = !=. A user name registered at that moment, or -.
- reviewer: the reviewer. = !=. A user name registered at that moment, or -.
- estimate: the estimate. = != < <= > >=. A string of 1 to 6 characters consisting only of digits (its decimal value), or -. However, - can be used only when the operator is = or !=.
- sprint: the issue's sprint. = !=. A sprint name existing at that moment, or -.
- comments: the comment count. = != < <= > >=. A string of 1 to 6 characters consisting only of digits (its decimal value).
- blocked: yes if the issue is blocked, no otherwise. = !=. yes or no.
- done: yes if the issue is done, no if it is not done. = !=. yes or no.
- title: the title. ~ only. Any string.

(5) Truth of a condition
For fields other than title, the value V - denotes "none" (for title, the value - is the character "-" itself). The truth of a condition for an issue is as follows.
- =: true when the issue's value and the value denoted by V are equal. "none" is equal only to "none".
- !=: true when = is false (example: for an issue whose estimate is "none", estimate!=3 is true).
- <, <=, >, >=: true when the relation holds when comparing the issue's value with the value denoted by V in this order. However, it is false when the issue's value is "none" (estimate of an issue with no estimate).
- ~: true when the title contains V as a contiguous substring. Here, uppercase and lowercase English letters are not distinguished (both are compared after converting their uppercase English letters to the corresponding lowercase letters).

[Output format]
- For each command, output the lines specified in [Processing] in the specified order. On an error, output only the single line starting with ERROR.
- Every separator within a line is a single ASCII space, and no line has whitespace at its start or end (spaces inside titles and comment texts are as in the input).
- Every integer is written in decimal notation without extra leading zeros.
- The output consists only of ASCII characters, every line ends with a newline (LF), and no empty lines are output.

[Constraints]
- 1 <= N <= 1000.
- The command name is one of those in the list, and the 2nd token of SPRINT is one of NEW, ADD, REMOVE, START and END. Each command has the number of tokens shown in the list, except that CREATE has 5 or more tokens, COMMENT has 4 or more, and QUERY has 2 or more.
- Each token always has the format given in [Input format]. Issue numbers, user names and sprint names that do not exist, and types, priorities, states, relations and points not in the lists, may be given.
- <day> is between 1 and 365 inclusive; <issue>, <issue1> and <issue2> are between 1 and 9999 inclusive; <points> is between 0 and 99 inclusive.
- <user> and <sprint> are 1 to 10 characters long; <type>, <priority>, <state> and <relation> are 1 to 12 characters long.
- <title> and <text> are strings of words separated by single ASCII spaces, where each word consists of English letters, digits and the symbols "'", "-", ":", ",", ".", "!", "?" and "&". <title> is 1 to 40 characters long and <text> is 1 to 60 characters long.
- <query> is a string of 1 to 100 characters consisting of the ASCII characters from "!" to "~" and ASCII spaces.
- At most 100 issues are created, at most 20 users and at most 20 sprints.

[Example]
Input:
25
USER ann
USER ben
CREATE 1 BUG HIGH Login button broken
CREATE 2 STORY MEDIUM Export to CSV
CREATE 3 TASK LOW Update docs
MOVE 1 IN_PROGRESS
MOVE 1 TRIAGED
ASSIGN 1 ann
MOVE 1 IN_PROGRESS
ESTIMATE 1 3
LINK 1 BLOCKS 3
MOVE 2 READY
ESTIMATE 2 5
MOVE 2 READY
SPRINT NEW s1
SPRINT ADD s1 2
SPRINT ADD s1 1
SPRINT START s1
DAY 3
REVIEWER 1 ben
MOVE 1 REVIEW
MOVE 1 RESOLVED
QUERY type!=TASK AND (status=READY OR assignee=ann)
QUERY priority>=HIGH OR
BURNDOWN s1
